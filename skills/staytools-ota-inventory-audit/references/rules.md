# 판정 규칙

## 🚨 먼저 — 지난 조사의 PMS 0 목록과 양방향으로 대조한다

PMS 잔여가 0 이하라 닫아둔 칸은 취소가 나서 방이 되살아나도 **OTA 쪽이 따라 열리지 않는다.** PMS 잔여만 움직이므로 화면 비교로는 안 잡힌다.
반대로 지난 목록에 없던 칸이 새로 0이 되면 양 채널이 열린 채일 수 있다. 한 숙소 관측: 지난 목록의 칸은 그대로인데 **새로 0이 된 칸이 양 채널 판매 중**인 일이 연속으로 나왔다.

프로필의 「기록 위치」에서 지난 조사의 PMS 0 목록을 열어 이번 목록과 대조한다. 칸은 `날짜|상품`으로 잡는다.
```js
const 되살아남=[...prev].filter(x=>!now.has(x));   // → 열 대상
const 새로0  =[...now ].filter(x=>!prev.has(x));   // → 전 채널이 닫혔는지 최우선 확인
```
- **되살아난 칸 → 연다.** 운영 예외와 `references/fix.md`의 저장 직전 재조회를 거친다.
- **새로 0이 된 칸 → 전 채널이 닫혔는지 가장 먼저 확인한다.** 한쪽이 닫혔다고 다른 쪽이 안전한 게 아니다.
- **"이 날은 열자/닫자"로 날짜 단위 판단을 하지 마라.** 판정은 언제나 날짜 × 상품 칸 단위다. 같은 날 한 상품은 닫을 대상, 다른 상품은 열 대상이 되기도 한다.
- 어제 연 칸을 오늘 닫는 건 실수를 되돌리는 게 아니라 그날의 정답을 맞추는 일이다.
- 지난 목록이 없으면 "대조 불가"로 적고, 이번 PMS 0 목록을 기록 위치에 남긴다.

## 🚨 고친 칸도 매번 전수로 다시 수집한다

한 숙소 관측: 마감으로 둔 칸이 다음 조사에서 **아무도 건드린 기억 없이 판매로 돌아가 있었다.** PMS 잔여는 내내 0이었고, 다른 채널은 마감 그대로였다. 원인은 확정하지 못했다.

→ "지난번에 고쳤으니 괜찮다"는 판단을 하지 마라. 어떤 칸도 건너뛰지 말고 **전수 수집 → 전수 판정**을 매번 한다.
→ 재고가 1실 같은 객실은 풀리는 즉시 오버부킹이다. 매 조사에서 날짜별 상태를 찍어 확인해라.

## ★ 제1원칙 — 재고 숫자가 아니라 오픈이냐 마감이냐

**재고를 몇 실로 넣느냐는 중요하지 않다. PMS에 방이 1실이라도 남아 있으면 OTA에서 팔리는 상태여야 한다.**

그래서 판정은 "재고가 몇이냐"가 아니라 **"지금 이 날짜에 이 방을 팔 수 있느냐"** 로 한다.
아래 셋은 전부 같은 문제다 — 표시만 다르지 결과는 "못 판다"로 똑같다.

| 화면 표시 | 실제 상태 |
|---|---|
| `마감` | 못 판다 |
| `매진` (재고 0 / 잔여 0) | **판매상태는 '판매'인데 못 판다** |
| `미설정` | 상품이 없어서 못 판다 |

**판매상태가 '판매'라는 이유로 정상이라고 넘기지 마라.** 야놀자는 `saleOpen:true`인데
`reservableQuantity:0`이면 매진이고, 여기어때는 `status:1`인데 `total_stock:0`이면 매진이다.
PMS 잔여가 있는데 이 상태면 **판매 손실이고, 재고를 올려서 여는 게 정답이다.**
재고 숫자를 얼마로 할지는 물어볼 일이 아니다 — 같은 상품의 다른 날짜 값을 그대로 쓰면 된다.


## 상품 ↔ 객실 매핑 (PMS 잔여를 어디에 대응시키나)

**매핑표는 프로필(`hotel-profile.md`)의 「OTA 상품 ↔ PMS 객실 매핑」이 기준이다.** 형식은 이렇다 (가상 예시):

| OTA 상품 | PMS 객실 | 비고 |
|---|---|---|
| 스탠다드 / 스탠다드 + 조식 | 스탠다드 | |
| 디럭스 / (디럭스로 배정하는 기획 상품) | 디럭스 | 기획 상품은 이름이 달라도 같은 객실 |
| 랜덤배정 특가 | (기준 객실) | 랜덤배정 — 아래 참고 |
| 한 채널 전용 상품 | (객실) | 그 채널에만 있다 |

이름이 비슷하다는 이유로 매핑을 단정하지 마라. 프로필에 없는 상품은 **매핑 미확인**으로 분리하고 잠정 판정이라고 적는다.
매핑은 추정이 섞인다. 판정이 뒤집힐 만한 건은 보고서에 "매핑 가정 때문에 달라질 수 있음"이라고 적어라.

**랜덤배정 상품**은 그날 다른 객실 타입에 여유가 있으면 열려 있어도 문제없다. 기준 객실 하나의 잔여만 보고 닫지 마라.

## 이건 정상이다 — 절대 건드리지 마라

아래 1·2·5·6은 **숙소가 프로필에 적어 둔 운영 예외**가 있을 때 적용한다. 예외가 적혀 있지 않으면 정상이라고 가정하지 말고 확인한다.

**1. 부대 서비스 미운영일의 포함 상품이 마감인 것**
예: 일요일 아침에 조식을 운영하지 않는 숙소라면 토요일 투숙(=일요일 조식) 조식 포함 상품은 예약불가가 맞다.
**연휴여도 그 요일이면 똑같이 적용된다.**
→ 반대로 **그 날짜에 포함 상품이 열려 있으면 그게 오류**다. 닫아야 한다.

**2. 상시 마감 상품**
특별한 경우에만 프런트에서 여는 상품은 마감이 기본값이다. 프로필에 "상시 마감"으로 적힌 것만 해당한다.

**3. `매진`(재고 0)이면서 PMS도 0인 것**
실제로 다 팔린 것. 정상. — 단 **PMS에 1실이라도 남아 있으면 매진은 정상이 아니다.** 제1원칙을 봐라.

**4. 오늘 날짜 — 조사 대상이 아니다**
재고 파악은 **오늘을 제외한 날짜**다. 당일 건은 건드리지도, **보고하지도** 않는다. 물어보지도 마라.
수집 단계에서 `date > 오늘`로 잘라내라 — 판정 목록에 올라오지 않게 하는 게 가장 확실하다.
("조치는 안 했지만 보고는 한다"도 범위 위반이다.)

**5. 오버부킹을 허용하는 객실 타입의 PMS 잔여가 0 또는 마이너스**

숙소가 특정 객실 타입에 오버부킹을 N실까지 받기로 했다면 **잔여 `-N`까지는 정상이고, `-(N+1)` 이하부터 위험이다.**
마이너스가 찍혔다고 바로 닫지 마라.

```js
// 프로필의 오버부킹 허용치: {객실타입: N}. 적혀 있지 않은 타입은 0
const allow = OVERBOOK[name] || 0;
위험 = (잔여 <= -(allow + 1));     // 허용치 N=15 이면 0도 -4도 -15도 정상, -16부터 위험
                                   // 허용치 0 이면 잔여 0부터 곧바로 위험
```

**이 예외는 프로필에 적힌 객실 타입에만 적용된다.** 이름이 비슷한 다른 타입(예: `스탠다드`와 `스탠다드 프리미어`)은
별개이고, 허용치가 없으면 **잔여 0이면 곧바로 오버부킹 위험**으로 올린다.
두 채널이 이미 마감이라 조치가 필요 없더라도 판정은 '위험'이 맞다.

PMS 잔여 필터는 반드시 `<= 0`으로. `=== 0`으로 잡으면 마이너스를 통째로 놓친다.

**6. 대실에서 운영 상품 외 나머지가 미설정인 것**
대실은 프로필의 「대실 운영 상품」만 운영한다. 나머지 상품의 미설정은 정상이다.

## 이건 문제다 — 우선순위 순

**A. 재고 미투입 (가장 크다)**
한 달 또는 여러 날이 통째로 `매진`(재고 0)이거나 `미설정`. PMS엔 방이 있다.
아무도 그 기간 재고를 안 넣은 것이고, 마감/오픈 토글로는 안 고쳐진다. **재고를 넣어야 한다.**
→ 다음 달·그다음 달도 같은 상태인지 반드시 같이 확인해라. 한 달을 고쳤더니 그다음 달도 똑같았던 사례가 있다.
→ 한 달이 통째로 닫힌 구간은 자동으로 열지 말고 보고한다 (`fix.md`의 「한 달 오픈」).

**B. 판매 손실**
PMS 잔여 > 0 인데 OTA에서 못 파는 상태 — `마감`이든 `매진`(잔여 0)이든 `미설정`이든 전부 여기다.
**판매상태만 보지 말고 잔여 재고가 0인지도 같이 봐라.** 배정이 1실인데 1실이 팔려서 잔여 0이 된 날은
화면상 '판매'로 보이지만 실제로는 닫힌 것과 같다.

**C. 오버부킹 위험**
PMS 잔여 0 인데 OTA는 `판매`. 위 5번 예외를 먼저 적용한 뒤 남는 것만.

**D. 채널 간 불일치**
두 OTA가 서로 다른 상태. 한쪽만 닫혀 있으면 그쪽이 손실이다.
재고가 CMS로 연동되지 않은 채널은 **한쪽을 고쳐도 다른 쪽은 자동으로 안 따라온다. 항상 양쪽 다 확인해라.**
