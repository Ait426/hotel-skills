## 물려받은 교훈 — 이 스킬을 만든 운영에서 실제로 겪은 것

아래는 야놀자(NOL)·여기어때 모텔 파트너센터와 YFlux PMS를 쓰는 숙소에서 누적된 교훈이다.
숙소 고유의 값(상품 이름·요금·허용치)은 뺐다. 그런 값은 `hotel-profile.md` 에 있다.

### 판정에서 틀렸던 것

**❌ 매진을 정상으로 넘겼다.**
한 채널의 상품이 `판매상태: 판매`인데 잔여 0(매진)이었다. PMS엔 1실 남아 있었다.
그런데 "이건 마감이 아니라 재고를 올리는 일"이라며 승인 대기로 빼놨다.
→ 판매상태 라벨이 아니라 **실제로 팔 수 있느냐**로 판정해야 한다. 이게 제1원칙이 됐다.
→ 재고를 얼마로 넣을지는 물어볼 일이 아니다. 같은 상품 다른 날짜 값을 쓰면 된다.
→ 스캔할 때 `saleOpen`/`status`만 보지 말고 **잔여 0을 같이 필터에 넣어라.**

**❌ 오늘 날짜를 "조치는 안 하고 보고만" 했다가 지적받았다.**
오늘 여러 상품이 마감인 걸 찾아서, 조치는 안 하고 표로 크게 보고했다.
→ **오늘 날짜는 조사 대상 자체가 아니다.** 조회·판정·**보고**·조치 전부 안 한다.
→ 수집 단계에서 `date > 오늘`로 잘라라. 판정 목록에 아예 올리지 않는 게 유일하게 확실한 방법이다.

**❌ 오늘이 며칠인지 틀렸다 (두 번).**
세션이 며칠에 걸쳐 이어지면 사용자 기억도, 앞 턴의 확인도 틀린다. 브라우저가 끊겼다 붙고 탭 ID가 바뀌고
캘린더 첫 날짜가 밀렸는데도 옛 날짜로 범위를 잡았다.
→ **매 조사 시작마다 브라우저 시계로 오늘을 먼저 확인해라.** 사용자 말도 대조 대상이다.
→ 교차 검증: 여기어때 캘린더의 `targetGoods.total[0].date`가 곧 오늘이다. PMS 화면 헤더의 날짜는 **영업일**이라 새벽에 하루 다를 수 있다. 갈리면 하루 더 보수적으로 제외한다.

**⚠ 상품이 늘어날 수 있다 — 상품 목록을 고정으로 가정하지 마라.**
한 채널에만 특정 며칠만 등록된 이벤트 상품이 새로 생긴 적이 있다. 판정 예외 목록에 없으면 매번 '판매 손실'로 오탐된다.
→ 매 조사마다 `T[0].rooms.map(r=>r.armgname)`로 **상품 이름 배열을 먼저 찍어** 늘거나 줄었는지 확인해라.
→ 새 상품은 손대지 말고 사용자에게 확인받아 프로필에 넣는다.

**⚠ PMS 잔여는 음수가 된다.**
필터는 반드시 `<= 0`으로. `=== 0`으로 잡으면 마이너스를 통째로 놓친다.
오버부킹 허용치가 있는 객실 타입은 허용치까지 정상이다 (`rules.md` 5번).

**❌ 미설정 상품이 한 날짜에 끼어든 걸 놓쳤다.**
작업 후 전수 확인에서 "전 날짜 상품 수 동일"로 봤는데, 하루만 상품 몇 개가 더 등록돼 있었다.
→ 저장 전 가드로 상품 수·이름만 확인하지 말고, **저장 후에도 날짜별 상품 수를 세어 봐야 한다.**
`T.forEach(d=>cnt[d.rooms.length]++)` 로 한 줄이면 잡힌다.

### 저장에서 틀렸던 것 (여기어때)

**❌❌ 가장 큰 사고 — 대실 페이지에서 `type:2`로 저장해 숙박 요금이 대실 요금으로 덮였다.**
대실 판매설정 페이지에서 상품을 열려고 `await st.updateSelectedGoods({type:2})` 를 호출했다.
`{result:true}` 를 받았고, 대실 캘린더를 다시 읽으니 여전히 마감이라 "저장이 안 먹었네" 하고 넘어갔다.
**실제로는 안 먹은 게 아니라 엉뚱한 데 먹었다.** `type:2`는 **숙박**이다(`st.routerParams.requestType`).
대실 상품의 값(요금·재고·이용시간)이 그대로 **같은 이름의 숙박 상품 이틀치에 덮어써졌다.**
판매량 0이라 실제 손해는 없었고, 나중에 숙박 요금을 훑다가 한 상품만 대실 요금대인 게 눈에 띄어 발견했다.
**전수 스캔을 안 했으면 못 잡았다.**
→ **`updateSelectedGoods` 호출 전에 `st.routerParams`를 반드시 찍어 `type`이 맞는지 확인해라.**
  숙박=`2`. 대실은 다른 값이고, **대실 상태/값 변경은 이 경로를 쓰지 마라.**
→ **"저장이 안 먹은 것 같다"는 순간을 그냥 넘기지 마라.** 못 먹은 게 아니라 **다른 곳에 먹었는지**를 먼저 의심해라.
→ 작업 후 전수 스캔에 **이상값 탐지**를 넣어라: 숙박에 대실 요금대가 있는지, 이용시간이 프로필 기준과 다른 상품이 있는지 (`fix.md`).

**❌ `updateSelectedGoods`로 대실 판매상태를 바꿨는데 서버에 안 들어갔다.**
`{result:true, saleStatus:false}` 를 받고 성공으로 봤는데, 다시 읽으니 여전히 `status:4`(마감)였다.
→ **`result:true`는 저장 성공의 증거가 아니다. `saleStatus` 필드도 성패 지표가 아니다.**
→ **판매상태 변경은 캘린더 하단의 `판매`/`준비중`/`마감` 버튼으로 하는 게 확실하다.**
  `updateSelectedGoods`는 요금·재고·시각 변경용으로만 쓰고, 상태를 같이 바꿨다면
  반드시 **다른 페이지로 갔다가 돌아와 새로 fetch한 뒤** 다시 읽어 확인해라.

**❌ 저장 직후 같은 배열을 읽고 "반영됐다"고 판단할 뻔했다.**
`selectedGoodsDatas`의 행과 캘린더 `targetGoods.total[i].rooms`의 행은 **같은 객체를 참조**한다.
로컬에서 `dpod_state`만 바꿔도 캘린더가 바뀐 것처럼 보인다.
→ 검증은 **반드시 재fetch 후**. `$router.push`로 다른 달/다른 탭에 갔다가 돌아오거나 `location.href`로 실제 로드를 시켜라.

**✅ 캘린더 하단 `판매` 버튼 경로가 정확하고 안전하다.**
1. 칩으로 상품을 좁힌다 → 2. 날짜 셀(`td label`)을 클릭해 선택
→ 3. `판매`(`.btn-color-type05`) 클릭 → 4. 모달 문구 확인 → 5. `확인`.
모달은 `.modal-content`에 있고 화면 밖에 렌더될 수 있으니 **DOM에서 좌표를 계산**해 눌러라.
문구: *"선택된 날짜의 상품을 모두 판매 상태로 적용하시겠습니까?"* — `모두`가 붙어 있으니
**칩으로 안 좁힌 상태에서는 절대 누르지 마라.**
- 날짜 셀 좌표는 `document.querySelectorAll('td label')`로 뽑는다. 체크박스 input이 없어서
  `label` 자체를 클릭해야 한다. **화면 밖 셀은 클릭이 씹히므로 먼저 스크롤**하고 다시 좌표를 뽑아라.
- ❌ 칩 필터가 **유지된다고 믿으면 안 된다.** 이동 직후 칩 하나만 켜져 있다가 **몇 초 뒤 전체 선택으로 풀리고 날짜 선택도 비워진** 관측이 있다. 그대로 누르면 전 상품이 마감된다. 누르는 호출 안에서 가드를 건다 (`fix.md`). 작업이 끝나면 반드시 전부 되돌려라.
- 칩을 껐다 켜는 클릭은 매번 캘린더를 refetch하므로 **2.5초 간격 setTimeout 루프**로 돌리고
  별도 호출로 진행 상황만 폴링하면 45초 타임아웃에 안 걸린다.
- 캘린더의 `targetGoods.total[i].rooms`는 **칩 필터와 무관하게 전 상품을 담는다.** 읽기는 좁혀도 된다.

**✅ 여기어때 상품 칩은 setup 화면의 `selectedGoodsDatas`를 그대로 좁힌다.**
칩 2개만 켜면 저장 payload에 그 2개만 들어가고 나머지는 손도 안 탄다 (수정 전/후 전수 diff로 검증).
→ 특정 상품만 고칠 땐 날짜를 tier로만 묶으면 된다. 재고 서명으로 그룹을 쪼갤 필요가 없다.

**⚠ 여기어때 `$router.push` 직후 데이터가 stale이다.**
다음 달 캘린더의 0번 슬롯에 이전 달 데이터가 얹혀 보인 적이 있다. 읽기 전에 `T[0].date`와
`rooms.length`를 먼저 확인하고, 이상하면 다시 읽어라.

- 여기어때 설정 화면의 `적용` 버튼은 폼 전송을 일으켜 **저장 XHR을 취소한다.** 누르지 말고
  `updateSelectedGoods({type:2})`를 직접 불러라 (숙박 페이지에서, 요금·재고·시각만).
- 여기어때 칩 클릭과 라우팅을 **같은 호출에 넣으면** 칩이 반영되기 전에 라우트가 잡힌다. 나눠라.
- 칩을 루프로 한꺼번에 되돌리면 `Runtime.evaluate`가 45초 타임아웃으로 죽는다. `setTimeout` 체인으로
  바꿔도 중간에 멈추니, **상태를 읽고 남은 것만 다시 돌리는 식으로 여러 번 나눠라.**

### 저장에서 틀렸던 것 (야놀자)

> **⚠ 2026-10 화면 변경 가능성 있음, 확인 필요.** 이 절은 이전 화면 기준일 수 있다. 판매설정이 전체 페이지로 열리고, 체크박스·셀렉트가 MouseEvent dispatch로 동작했다는 관측이 있다 (`fix.md`의 「야놀자 판매설정 모달」). 포털에서 재검증하지 못했다.

**❌ 좌표 클릭이 엉뚱한 날짜를 잡았다 — 저장 직전에 발견.**
카드를 좌표로 클릭했는데 하루 앞 날짜가 선택됐다. 판매설정 화면의 날짜 칩을 읽고서야 알았다.
→ **판매설정 화면을 연 직후 날짜 칩(`\d\d\.\d\d\(.\)`)을 반드시 읽어 의도한 날짜인지 확인해라.**
  이 확인 없이는 절대 저장하지 마라.
→ 좌표 클릭은 카드 안의 `예약 N` 링크를 때려 **새 탭이 열리는** 일도 잦다.

**✅ 야놀자 카드 선택은 좌표 말고 JS 이벤트 디스패치로.**
```js
const cards=[...document.querySelectorAll('*')].filter(e=>{const t=(e.textContent||'').replace(/\s+/g,' ').trim();
  return /^(판매|마감|매진|준비)?<상품명>/.test(t) && t.indexOf('원')>-1 && t.length<80;});
// 카드에서 부모로 올라가며 '숫자로 시작하는' 날짜 셀을 찾아 날짜를 구한다
// 상품명 span에 클릭 이벤트를 쏜다 (예약 링크를 피하려고)
span.dispatchEvent(new MouseEvent('click',{bubbles:true,cancelable:true,view:window}));
```
MUI 셀렉트도 같은 방식: `sel.dispatchEvent(new MouseEvent('mousedown',{bubbles:true,...}))`로 열고
옵션 `li`에 `click`을 쏜다. **단, MUI 체크박스(객실 필터)만은 이 방법도 좌표 클릭도 안 먹는다.**
(⚠ 2026-10 화면 변경 가능성 있음, 확인 필요 — `.MuiListItemButton-root` 행에 dispatch하면 동작했다는 관측이 있다.)

**⚠ 야놀자 캘린더 가상스크롤이 자주 안 그려진다.**
`window.scrollTo`로는 상품 카드가 mount되지 않는다. DOM에 아예 없어서 쿼리가 빈 배열을 준다.
→ **`computer` 도구의 wheel 스크롤을 써라.** 진짜 스크롤 이벤트라야 가상 리스트가 그려진다.
→ 판매설정 다이얼로그도 같다. `window.scrollTo(0,0)` + **스크린샷 1장**을 찍으면 그제야 입력창이 mount된다.
→ 화면이 새하얗게 찍히면 페이지가 죽은 게 아니라 그 스크롤 위치에서 페인트가 안 된 것이다.

**✅ 야놀자 재고 올리기 — 네이티브 setter.**
`roomtypeInventories.<i>.inventories.0.reservableQuantity`가 **잔여**다.
```js
const setter=Object.getOwnPropertyDescriptor(window.HTMLInputElement.prototype,'value').set;
setter.call(inp,'1'); inp.dispatchEvent(new Event('input',{bubbles:true}));
inp.dispatchEvent(new Event('change',{bubbles:true}));
```
저장 전에 **모든 행의 값을 찍어 다른 행이 안 바뀌었는지 확인**하고, 저장 후 API로 재조회해 검증한다.

- **야놀자 대실 상세의 재고 입력칸은 `reservableQuantity`(잔여)다.** `quantity`(배정 총량)가 아니다.
  1실 배정 중 1실 팔린 날은 0으로 보인다. 여기에 1을 넣으면 총량이 2가 된다.
- **야놀자 `요금 및 재고 관리`(요금표)는 미설정 일자에만 일괄 반영된다.** 이미 등록된 날짜는
  안 건드린다. 대신 요일 기준이라 공휴일 tier는 표현 못 하므로, 공휴일이 낀 달엔 캘린더로 해야 한다.
- **야놀자 객실 드롭다운의 `적용(N)` 숫자는 상품 수가 아니다.** 하위타입이 같이 세어진다.
  놀라서 되돌리지 마라 — 목록의 체크 상태로 확인해라.
- **드롭다운 하단 `전체선택`이 리스트 마지막 항목과 10px 차이로 겹친다.** 좌표로 누르지 말고 `find` + ref 클릭이 안전하다.
- 야놀자는 **fetch가 아니라 XHR(axios)** 이다. `window.fetch`만 후킹하면 아무것도 안 잡힌다.
- 야놀자 라우터는 `history.pushState` + 합성 `popstate`로 안 움직인다. **실제 UI 클릭이 필요하다.**
- 야놀자 MUI 셀렉트는 좌표 클릭 후 `Home` → `ArrowDown ×N` → `Return`. 키 사이에 텀이 없으면 조용히 실패한다.
- 빨간 **`일괄 마감`** 은 절대 누르지 마라.
- 야놀자 공지 모달이 다시 뜬다. 달 이동 클릭이 안 먹으면 공지 모달부터 의심해라. 좌표 클릭 말고 JS로 닫는다.
  ```js
  [...document.querySelectorAll('[role="dialog"],.MuiDialog-root,.MuiModal-root')]
    .forEach(d=>{const b=[...d.querySelectorAll('button')].find(x=>x.textContent.trim()===''); if(b)b.click()});
  ```

### 공통

**❌ 좌표를 스크린샷에서 눈으로 찍었다.**
스크린샷 픽셀과 클릭 좌표계는 탭마다 배율이 다르다.
→ **항상 DOM에서 `getBoundingClientRect() × (1568/innerWidth)`로 계산해라.** 예외 없다.
(⚠ 2026-10 화면 변경 가능성 있음, 확인 필요 — 브라우저 줌이 걸리면 이 공식이 어긋난 관측이 있다. 이때는 좌표를 쓰지 않고 dispatch를 쓴다.)

**⚠ 브라우저가 두 대 연결돼 있을 수 있다.**
`javascript_tool`이 45초 타임아웃 나고 스크린샷이 "Cannot access contents of the page"로 막히면
**끊긴 게 아니라 엉뚱한 Chrome에 붙은 것**일 수 있다. `list_connected_browsers`로 확인하고,
두 대 이상이면 반드시 사용자에게 물어라. `switch_browser`가 제일 확실하다.
페이지 전역(`window.__*`)은 이때 다 날아가 있으니 헬퍼부터 다시 심어라.

**⚠ 사이트별 로그인이 따로 논다.**
PMS와 두 채널이 각각 다른 시점에 로그아웃돼 있을 수 있다. 조사 시작 전에 전부 확인해라.
로그인은 며칠씩 유지되는 편이라 매일 다시 로그인할 필요는 없다. 끊겨 있으면 해당 사이트만 사용자에게 알린다.

**⚠ PMS API가 간헐적으로 빈 배열을 준다.** 한 달씩 끊어도 그렇다. 빈 배열이면 재시도하고,
그래도 안 되면 다른 날짜 구간으로 우회해라. **빈 배열을 "잔여 0"으로 읽으면 안 된다.**

**✅ 수정 전 데이터를 파일로 남겨두면 "안 건드렸다"를 증명할 수 있다.** 저장 후 전수 diff를 돌려
의도한 칸만 바뀌었는지 보여주는 게 "확인했다"는 말보다 훨씬 낫다.

**⚠ 통째로 죽어 있는 먼 달은 임의로 열지 마라.**
몇 달 뒤가 두 채널 모두 마감/재고0/미설정이고 요금도 옛 기본값 단일가인 경우가 있다.
운영자가 "지금은 열지 마라"고 한 구간일 수 있다. 발견은 보고하되 조치는 지시를 받고 한다.
