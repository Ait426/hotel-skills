# 부킹닷컴 요금 운영

숙소의 부킹닷컴 요금·프로모션을 다룰 때 이 절차를 따른다.
**이 배포본에는 특정 숙소의 값이 없다.** 숫자는 전부 「숙소 프로필」에서 온다.

## 시작 — 숙소 프로필을 먼저 확정한다

1. 작업 폴더나 이 스킬 폴더에 `hotel-profile.md` 가 있으면 읽는다.
2. 없으면 `hotel-profile.example.md` 양식의 항목을 사용자에게 받거나, 익스트라넷·CMS 화면에서 읽어 채운다.
3. **프로필에 없는 값은 지어내지 않는다.** 본문과 양식의 숫자는 형식 예시다 — 다른 숙소의 값을 복사하지 마라.

계산에 반드시 필요한 것: 판매가(요금세트별) · 요금제 배수 · 기준 인원과 인원 계수 ·
타겟 요금 할인율 · 포트폴리오형 할인율 · 캠페인 · **입금 계수(실예약으로 역산한 값)** · 입금가 하한.
하나라도 없으면 그 항목을 "미확인"으로 표시하고, 그 값이 필요한 계산은 확정값이라고 쓰지 않는다.

**브라우저 도구가 없는 환경이면** 프로필 값으로 계산까지만 한다. 익스트라넷 재조회(3장)와 소비자 페이지 역산(8장)은
"실측 미확인"으로 남기고, 사용자가 직접 확인할 수 있게 조회 조건(체크인 날짜·박수·인원)을 적어 준다. 변경은 "변경안"으로만 쓴다.

## 0. 절대 규칙

1. **로그인은 사용자가 직접 한다.** 비밀번호를 절대 입력하지 않는다. 세션이 풀리면 재로그인을 요청한다.
2. **저장·적용 버튼은 프로필의 「버튼 정책」을 따른다.** "에이전트가 끝까지 누른다"로 돼 있으면 변경 지시를 받은 범위에서 불가능한 것만 빼고 실행한다. 기록이 없으면 저장 직전에 멈추고 사용자에게 맡긴다.
3. **설정 화면만 보고 「됐다」고 하지 않는다.** 항상 소비자 페이지에서 역산해 확인한다.
4. **매 턴마다** 확인·판정·계산을 사용자가 지정한 작업 문서에 기록한다. (지정이 없으면 어디에 남길지 한 번 묻는다.)
5. **프로필의 입금가 하한**을 뚫는 변경은 하지 않는다. 뚫릴 것 같으면 먼저 계산해서 보고한다.
6. **부킹 채널만** 담당한다. 다른 채널은 비교 근거로만 쓴다.
7. 예약·투숙객의 이름·연락처·예약번호는 결과물과 기록에 넣지 않는다.
8. **요금 답변 전에 소비자 페이지에서 예약 가능 여부부터 본다** (12장). 확인할 도구가 없으면 "예약 가능 여부 미확인"이라고 쓴다.

## 1. 접속 정보 — 프로필에서 읽는다

| 대상 | 주소 |
|---|---|
| 익스트라넷 | `admin.booking.com` (hotel_id = 프로필의 숙소 ID) |
| 소비자 페이지 | `booking.com/hotel/{국가코드}/{숙소-슬러그}.ko.html` |
| CMS 판매가 | 프로필의 채널 매니저 주소 · 부킹용 상품그룹 |

채널 매니저를 안 쓰는 숙소는 판매가를 익스트라넷 요금 캘린더에서 직접 읽는다.

## 2. 요금 계산 구조 — 5단 곱셈

```
노출가 = 판매가
       × 요금제 배수        (기준 요금제 1.00 / 환불불가·주간·월간 등은 각자의 배수)
       × 숙박인원 계수      (기준 인원 1.00, 1명 적을 때마다 일정 폭 감액  ※ 곱하기 아니라 빼기: 계수 = 1 − 감액폭 × 줄어든 인원)
       × 타겟 요금 배수     (국가별(Domestic/International) | 모바일 중 하나)
       × (1 − 포트폴리오형)  (베이직 | 조기예약 | 막바지 중 하나)

입금가 = 노출가 × 입금 계수   ← 부가세 포함 기준인지 프로필에서 확인 (채널마다 기준이 다르다. 직접 비교 금지)
```

배수·계수·할인율은 전부 프로필 값이다. 입금 계수는 **최근 실예약의 결제·정산 내역으로 역산한 값**을 쓴다
(`입금 계수 = 실입금 ÷ 그 예약의 노출가`). 계약 수수료율만으로 추정한 값은 "추정"이라고 표시한다.

금액은 **반올림하지 않은 노출가에 입금 계수를 곱한 뒤** 원 단위로 반올림한다 (노출가를 먼저 반올림하면 1원씩 어긋난다).

**중복 규칙 — 같은 카테고리 안에서는 큰 할인 하나만.**
- 타겟 요금끼리 ❌ / 포트폴리오형끼리 ❌ / 타겟 × 포트폴리오형 ✅
  (국내 접속이면서 모바일이면 국가별 요금과 모바일 요금 중 **큰 할인 하나**가 걸린다)
- **베이직과 조기예약은 곱해지지 않는다.** 사전예약 손님은 조기예약만 걸린다.
- **요금제도 하나만 선택된다.** 환불불가 배수 × 주간 배수는 일어나지 않는다.
- **캠페인은 Genius 미참여 숙소에서 숙소의 조합을 대체한다** (곱해지지 않음). 큰 쪽 하나만.
- **Genius에 참여한 숙소는 Genius와 캠페인이 중복된다.** 계산 전에 프로필에서 Genius 참여 여부를 확인한다.
- **집중형 특가는 어떤 할인과도 중복되지 않는다.** 기본요금에 단독으로 걸린다.
- **막바지 특가는 「당일 1박」이 아니라 예약 전체 박수에 걸린다.** 조건을 만족하면 그 예약의 모든 숙박일에 할인이 붙는다 (한 숙소 관측: 다박 예약의 전 박 할인).
  최대 숙박일 제한이 없어 제도로 못 막는다. 맞춤 설정은 요금제와 객실 · 예약 가능한 시간대 · 최소 숙박일수뿐이었다.
  대응은 할인율을 낮추거나 예약창을 좁히는 것뿐이다.

| 카테고리 | 중복 가능 대상 |
|---|---|
| 프리미엄 (Genius) | 타겟 요금 · 포트폴리오형 · 캠페인 전부 |
| 타겟 요금 (모바일 · 국가별) | Genius · 포트폴리오형 |
| 캠페인 특가 | Genius만 |
| 포트폴리오형 (베이직 · 막바지 · 조기예약) | Genius · 타겟 요금 |
| 집중형 특가 (기간 한정) | 없음 |

중복 규칙 원문은 익스트라넷 「최대 할인 시뮬레이션」(`promotions/stacking_calculator.html`)에 문장으로 적혀 있다. 추측하지 말고 거기서 확인한다.

이 규칙은 원본 계정의 실예약 역산으로 확인한 것이다. **새 계정에서는 소비자 페이지 역산(8장)으로 한 번 확인하고 쓴다.**
맞지 않으면 그 계정에서 관측한 규칙을 프로필에 적고 그걸 따른다.

### 계산 예시 (가상 숙소 — 형식만 본다)

판매가 200,000 · 환불불가 0.95 · 기준 인원 · Domestic 25%(배수 0.75) · Basic 15% · Early Booker Secret 20% · 입금 계수 0.82 · 하한 90,000

| 칸 | 계산 | 노출가 | 입금가 | 하한 대비 |
|---|---|---:|---:|---:|
| 평시 · 기준 요금제 · 비회원 | 200,000 × 1.00 × 1.00 × 0.75 × 0.85 | 127,500 | 104,550 | +14,550 |
| 최심 (배수가 가장 낮은 요금제 × 사전 × 회원) | 200,000 × 0.95 × 1.00 × 0.75 × 0.80 | 114,000 | 93,480 | +3,480 |

## 3. 현재 설정값 — 프로필에 적고, 쓰기 전에 화면에서 다시 읽는다

프로필의 「현재 설정값」 표가 기준이다. **그 표는 스냅샷이다.** 변경 작업 전에는 익스트라넷에서 현재 값을 다시 읽어
표와 다르면 표를 먼저 고친다. 표에 담을 것:

- **판매가** — 객실 × 요금세트(WEEK / FRI / SAT 등)
- **프로모션** — 카테고리(타겟 요금 / 포트폴리오형 / 캠페인) · 이름 · 할인율 · 조건(리드타임·회원 전용)
- **종료 상태로 유지할 프로모션** — 일부러 꺼 둔 것
- **요금제** — 기준 요금제와 각 요금제의 배수(「요금 차이」)
- **결과** — 대표 객실의 평시 칸과 최심 칸의 노출가·입금가·하한 대비 여유

부킹이 강제하는 범위(예: 국가별 요금의 상한, 모바일 요금의 최소 할인율, 정수만 입력)는 화면의 입력 검증 문구에서 읽어
프로필에 적는다. 이미 상한이면 그 레버는 못 쓴다.

## 4. 요금세트는 요일이 아닐 수 있다

요금세트를 날짜에 어떻게 붙이는지는 숙소의 규칙이다. 프로필에 적힌 규칙을 따른다.
많이 쓰는 규칙은 「내일이 쉬는 날이냐」 기준이다.

| 오늘 | 내일 | 세트 |
|---|---|---|
| 근무 | 휴무 | **FRI** |
| 휴무 | 휴무 | **SAT** |
| 그 외 | | **WEEK** |

「휴무」 = 토·일 + 공휴일. 이 규칙이면 평범한 일요일은 WEEK, 연휴 중간 일요일은 SAT다.
**세트 이름(WEEK/FRI/SAT)을 요일로 읽지 마라.** 특정 세트가 매핑돼 있지 않은 것이 설계일 수 있다 — 오류라고 단정하기 전에 프로필을 본다.

## 5. 국적으로는 못 나눈다

부킹의 타게팅 축은 **접속 위치(IP·POS) / 기기 / 회원 여부** 셋뿐이다. **국적 타게팅은 존재하지 않는다.**

실예약을 역산하면 확인된다 — 국내에서 접속해 예약한 외국인 손님은 내국인과 똑같이 Domestic 요금을 받는다.
국내 거주 외국인 손님이 많은 숙소에서는 Domestic 예약 비중이 국적상 내국인 비중보다 높게 나온다.

→ **「외국인에게 더 받자」는 부킹에서 「국내 접속 손님에게 더 받자」로 작동한다.** 문서·표 라벨은 「국내접속 / 해외접속」으로 쓴다.

## 6. 객실 이름 매핑 (CMS ≠ 부킹)

CMS의 객실명과 부킹 소비자 페이지의 객실명은 다르다. 프로필의 매핑표를 쓴다.
매핑표가 없거나 의심스러우면 **이름으로 맞추지 말고 금액으로 역산해 확인한다**:
`소비자 페이지 「기존 요금」 ÷ (요금제 배수 × 인원 계수 × 타겟 요금 배수) = 판매가`.

## 7. 화면 조작 절차

### 7-0. 세션 관리 (제일 많이 깨지는 부분)
- 익스트라넷 안에서는 **`ses=` 가 붙은 상단 네비게이션으로 이동**한다.
- **`ses=` 없는 링크는 메뉴·인박스 링크라도 로그아웃될 수 있다.** 클릭 전에 href를 확인하고, 없으면 누르지 말고 `ses=` 가 있는 상단 메뉴로 간다.
  ```js
  [...document.querySelectorAll('a')].map(x=>({t:x.innerText.trim(),ses:/[?&]ses=/.test(x.href)}))
  ```
- **주소창 직접 입력 금지 · `location.reload()` 금지** — 로그아웃된다.
- 소비자 페이지 확인은 **반드시 새 탭**에서.
- 드롭다운이 「시스템에 오류가 발생했습니다」를 뱉으면 한 번 더 클릭하면 열린다.

### 7-1. 프로모션 할인율
```
프로모션 ∨ → 적용 중인 프로모션 확인하기 → 해당 행 「∨」 → 「수정」
 → #usp-discount-action 에 값 입력 (네이티브 setter)
 → 「검토」 실제 클릭 → 스크린샷 → 모달 없으면 한 번 더 → 스크린샷
 → 모달에서 할인율·대상 고객층·이름 확인 → 「적용」
```
```js
const setter=Object.getOwnPropertyDescriptor(window.HTMLInputElement.prototype,'value').set;
el.focus(); setter.call(el,'22');        // '22' 자리에 넣을 할인율
el.dispatchEvent(new Event('input',{bubbles:true}));
el.dispatchEvent(new Event('change',{bubbles:true})); el.blur();
```
- 「검토」는 **JS click이 안 먹는다.** 실제 마우스 클릭이어야 한다.
- **두 번 누르면 열린 모달이 닫힐 수 있다.** 반드시 스크린샷으로 확인하며 진행.
- 모달이 안 뜨면 값이 살아있는지 먼저 확인하고 다시 클릭.

### 7-2. 요금제 배수 (주간·월간·환불불가)
```
요금 및 예약 가능 여부 ∨ → 요금제 → 해당 행 「∨」 → 「수정」
 → 「요금 차이」의 「수정」 → 숫자 → 「저장」 → 하단 「변경사항 적용」
```
- 펼친 패널의 파란 「수정」 **바로 옆이 빨간 「삭제」**다. 좌표를 정확히.
- 「저장」만 누르면 반영 안 된다. **「변경사항 적용」까지.** 초록 배너로 확인.
- **주간과 월간은 별개 요금제다. 각각 고친다.**

### 7-3. 판매가 (CMS — WINGSCMS 계열을 쓰는 숙소의 예)
- 상품그룹 select는 **JS focus 후 실제 방향키**로 선택. 클릭+방향키는 안 먹는다.
- 화면의 "…를 (부킹 상품그룹) 로 복사 합니다." 안내 문구로 대상 그룹을 확인.
- 창이 작으면 그리드 입력칸이 안 잡힌다 → **1600×1000으로 리사이즈**.
- **저장 판정은 모달로 하지 않는다.** 에러 모달(「시스템 처리중에 문제가 발생했습니다」)이 떴는데 저장된 경우와 안 된 경우가 둘 다 관측됐다.
- 저장 후 **2~3분 기다린 뒤 재조회**한다. 그동안 **재입력·상품그룹 전환 금지** — 처리 중에 겹치면 모달이 뜨고 같은 값을 두 번 넣게 된다.
- 요금ID가 새 값으로 바뀌었으면 저장된 것이다. 2~3분 뒤에도 옛 값이면 그때 다시 넣는다. 최종 판정은 소비자 페이지 역산(8장)으로 한다.

다른 채널 매니저를 쓰면 그 화면의 저장·반영 절차를 프로필에 적어 두고 따른다.

## 8. 검증 — 소비자 페이지 역산 (필수)

```
https://www.booking.com/hotel/{국가코드}/{숙소-슬러그}.ko.html
  ?checkin=YYYY-MM-DD&checkout=YYYY-MM-DD&group_adults={기준 인원}&no_rooms=1&selected_currency=KRW
```

| 목적 | 체크인 | 박수 |
|---|---|---|
| 평시 할인 | 오늘+2~3일 | 1박 |
| 사전예약 할인 | 조기예약 조건을 넘는 날짜 (예: D-7 조건이면 오늘+8~10일) | 1박 |
| 요금제 배수 | 위와 같은 날짜 | 주간 요금제면 7박 |

**`group_adults`는 반드시 그 객실의 기준 인원으로.** 더 적은 인원으로 조회하면 숙박인원 계수 때문에 낮게 나와 오판한다.

읽는 법: **「기존 요금」** = 포트폴리오형 할인 **전** (판매가 × 요금제배수 × 인원계수 × 타겟요금). **「표시 요금」** = 포트폴리오형까지 뺀 값. 배지 「N% OFF」 = 포트폴리오형 할인율.

반영 시차 (한 숙소 실측. 부킹은 공식 반영 시간을 안내하지 않는다):

| 바꾼 것 | 소비자 페이지 반영 | 판정 |
|---|---|---|
| 값 — 프로모션 할인율 · 요금제 배수 · CMS 판매가 | 약 2~3분 | 3분 뒤 재조회. 요금제 배수는 새로고침까지 해서 본다 |
| 범위 — 프로모션 적용 객실 · 요일 | **25분이 넘어도 미반영 관측** | 당일 조회로 판정하지 않는다. 다음 날, 새로 예약창에 들어오는 날짜로 본다 |

반영이 안 보이면 먼저 익스트라넷 설정을 재조회해 저장 자체가 됐는지 분리한다.

**검색 카드는 우리 값이 아닐 수 있다.** 카드 대표 줄이 제3자 요금이거나 타 채널 객실명일 수 있고, 직판보다 싸게 뜰 수도 있다 (한 숙소 관측).
- 경쟁력 비교는 **숙소 상세 페이지의 직판 줄끼리** 한다. 카드 값은 「손님이 처음 보는 값」으로 따로 적는다.
- 판매 조건·가격을 바꾸면 **상세 페이지와 검색 카드를 둘 다** 확인한다. 카드 대표 줄이 제3자 요금이면 우리 변경이 카드에 안 실린다.

계산값과 실측값이 **원 단위로 일치**할 때까지 맞춘다. 몇 백 원 차이가 나면 빠뜨린 계수가 있다는 뜻이다.
정산 금액은 소비자 페이지에 없다 — 입금가를 "확인했다"고 쓰려면 예약의 결제·정산 내역까지 가야 한다.

## 9. 설계 규칙

**순서 제약** — `베이직공개 ≤ 조기공개 ≤ 조기시크릿`, `베이직공개 ≤ 베이직시크릿 ≤ 조기시크릿`.
어기면 비회원이 회원보다 싸지거나 사전예약이 평시보다 비싸진다.

**막바지 특가를 최심 칸에 넣는다.** 막바지는 예약 전체 박수에 걸리므로 다박 전용 요금제에도 걸린다.
칸을 펼칠 때 요금제 × 포트폴리오 최댓값(베이직 / 조기예약 / 막바지)까지 곱하고, 막바지가 일부 객실에만 걸리면 그 객실에서 따로 본다.
막바지가 조기시크릿보다 깊으면 아래 부등식의 `조기시크릿` 자리에 막바지 할인율을 넣는다.

**하한 제약** — 표를 채우기 전에 부등식부터 쓴다.
```
최심 노출가 / 헤드라인 노출가 ≥ 목표하한 / 목표헤드라인
좌변 = 요금제배수 × (1 − 조기시크릿) / (1 − 베이직공개)      ← 요금제배수 = 배수가 가장 낮은 요금제
```
이 부등식은 헤드라인을 목표값에 딱 맞출 때의 조건이다. 실제 헤드라인 입금가가 목표보다 높으면 여유가 더 있으니,
최종 판정은 항상 **최심 칸 입금가 ≥ 하한**을 직접 계산해서 한다.
요금제 배수가 이미 폭을 먹는다(0.95면 5.3%). 예: 하한 60,000 · 헤드라인 66,000 · 배수 0.95면
사다리에 남는 폭은 `(66,000 ÷ 60,000) × 0.95 − 1 = 4.5%`뿐이다.

**하한은 최고가 칸부터 검증한다.** 순서 제약 때문에 `최고가 ≥ 최심 ÷ 요금제배수`. 하한을 올리면 최고가도 끌려 올라간다. 최고가 칸이 이미 하한 아래면 「이건 하한 조정이 아니라 요금 인상입니다」라고 먼저 말한다.

**「불가능」이 나오면 내가 깐 전제를 먼저 의심한다.** 실제로 한 번 틀렸다 — 「조기시크릿 = 베이직+고정 폭」이라는 없는 전제 때문에 달성 가능한 목표를 불가능이라고 답했다. 채널이 강제하는 제약만 남기고 다시 푼다.

## 11. 출력과 기록

결과는 항상 이 순서로 낸다.

1. **현재 설정표** — 프로필 기준 + 화면에서 다시 읽은 값 (다르면 표시)
2. **계산표** — 칸별(요금제 × 리드타임 × 회원 × 접속) 노출가 / 입금가 / 하한 대비 여유
3. **실측 대조** — 소비자 페이지 「기존 요금」「표시 요금」과 계산값, 차이
4. **변경 목록** — 화면에서 무엇을 몇 %로 고칠지, 변경 전 값, 되돌리기 절차
5. **미확인 항목** — 근거 없이 쓴 값이 무엇인지

기록은 사용자가 지정한 작업 문서에 남긴다. 시간순 로그에는 **폐기된 판정을 지우지 말고 「폐기」 표시와 정정 사유**를 남긴다 —
다음 세션이 오답을 물려받지 않게 하기 위해서다. 운영 중 새로 밟은 함정은 프로필의 「함정 메모」에 추가한다.

## 12. 판매 정지 대응

**요금 질문에 답하기 전에 예약 가능 여부부터 본다.** 기록만 보고 할인율 표를 읊으면 판매가 멈춘 것을 놓친다.

```js
({ nameOK: document.body.innerText.includes('{프로필의 숙소명}'),   // false면 URL 오류. 정지로 판정하지 않는다
   blocked: /예약하실 수 없습니다|현재 저희 사이트에서/.test(document.body.innerText),
   rows: document.querySelectorAll('#hprt-table tr').length })
```
`nameOK` 가 true이고 `blocked` 가 true이거나 `rows` 가 0이면 판매 중단이다. 이때는 요금 답변보다 **판매 중단 사실을 먼저** 보고한다.
숙소 주소는 추측하지 말고 프로필이나 익스트라넷에서 가져온다.

1. **원인은 인박스 원문으로 확인한다.** 설정 화면보다 메시지 인박스를 먼저 연다.
   정지 전에 독촉 → 최후통첩 → 정지 통보가 날짜와 함께 남는다. 최후통첩의 마감일이 정지 시점의 확정 근거다.
2. **트리거와 현재 걸림돌을 나눠 쓴다.** 정지를 일으킨 것과 지금 정지를 유지시키는 것은 다를 수 있다.
   인과를 주장하면 시간순부터 본다 — 원인의 발효 시점이 정지보다 앞서야 한다. 독촉 날짜보다 늦게 발행된 청구서는 그 독촉의 대상이 아니다.
3. **청구서는 건별 상태로 기록한다.** 총액 한 줄로 적지 않는다. 번호 · 발행일 · 대상 기간 · 기한 · 상태 · 금액을 작업 문서에 적는다.
   「처리 중」은 납부 접수 상태이고, 「기한 경과」가 실제 위험 신호다.
4. **납부 후 재오픈은 자동이 아니다.** 부킹 공식 안내 순서는 이렇다.
   모든 미납 청구서 납부 → 부킹의 납부 확인 대기(최대 7일) → 상태가 「닫힘 - 재오픈 준비」로 변경 → **「내 숙소 오픈하기」를 직접 눌러야** 예약 접수 재개.
   납부일과 재개일은 다르다. 상태를 끝까지 추적한다.

납부는 사용자가 직접 한다.
