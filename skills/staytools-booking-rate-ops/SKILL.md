# 부킹닷컴 — 조사 · 계산 · 운영 · 콘솔

**이 배포본에는 특정 숙소의 값이 없다.** 숫자는 전부 그 숙소의 자료에서 온다.
`properties/example-hotel-0000000.json` 은 형식을 보여 주는 **가상 숙소**다. 그 숫자를 다른 숙소 계산에 쓰지 마라.

## 인자 처리 — 이게 최우선이다

숙소 ID(숫자)만 받고 호출되면 **묻지 말고 전체 흐름을 끝까지 돌려라.** 사전 점검 → 측정 → 공식 대조 → property.json → HTML → 전달까지다.

```
/staytools-booking-rate-ops                  로그인된 계정의 숙소를 찾아 조사 → HTML
/staytools-booking-rate-ops 1234567          그 숙소를 조사 → HTML
/staytools-booking-rate-ops 샘플 스테이        이름으로 찾아 조사 → HTML
/staytools-booking-rate-ops 1234567 계산만    조사 없이 저장된 값으로 계산
```

- 숙소가 여럿이고 이름도 없으면 목록을 보여 주고 고르게 한다.
- 로그인이 안 되어 있으면 사용자에게 요청하고 기다린다. 대신 로그인하지 마라.
- 막힌 영역은 `null` 과 `open[]` 에 남기고 나머지를 끝까지 진행한다. 한 영역 실패로 멈추지 마라.
- 입금가 하한과 목표처럼 **사용자만 정할 수 있는 값**은 지어내지 않는다. 없으면 비워 두고 보고에 적는다.

### 브라우저 도구가 없을 때 — 자료를 받아서 진행한다

익스트라넷을 읽을 도구가 없으면 조사를 지어내지 마라. 사용자가 준 자료(화면에서 옮긴 값, 정산서)로 `property.json` 을 채워 계산과 HTML 생성까지 한다.
익스트라넷 재조회와 소비자 페이지 역산은 "실측 미확인"으로 남기고, 사용자가 직접 확인할 수 있게 조회 조건(체크인 날짜·박수·인원)을 적어 준다. 변경은 "변경안"으로만 쓴다.

**최소 입력:** 숙소명 · 숙소 ID · 객실별 판매가와 기준 인원 · 요금제 배수 · 인원 감액폭 · 프로모션 목록(카테고리, 할인율, 조건) · 입금 계수.

끝나면 반드시 이 셋을 낸다.
1. HTML 파일 (전달 도구가 없으면 저장 경로)
2. 측정값 표 (각 값이 어느 화면·자료에서 나왔는지 포함)
3. 못 읽은 것과 그 이유

## 먼저 — 무슨 요청인지 가른다

| 사용자가 말한 것 | 할 일 | 읽을 것 |
|---|---|---|
| "입금가 얼마", "요금 얼마로 올려야 하나", "이 프로모션 켜도 되나" | 계산만 | `references/pricing.md` → `scripts/payout.py` |
| "실측했어?", "소비자 페이지 확인해", "입금가가 이상하다" | 실측 대조 | `references/measure.md` → `payout.py booking` |
| "요금 바꿔줘", "프로모션 고쳐줘" | 변경 + 검증 | `references/portal-map.md` → `references/measure.md` |
| "점검해줘", "현황 봐줘", "뭐가 부족해", "숙소 조사해줘" | 점검 + 조사 + 콘솔 | `references/audit.md` → `references/portal-map.md` → 아래 전체 흐름 |
| "후기 점수", "추천 숙소", "Genius 자격", "숙소 페이지 점수", "사진" | 점검만 | `references/audit.md` |
| "콘솔 만들어줘", "계산기 만들어줘" | 생성 | `assets/property.example.json` → `scripts/build_console.py` |
| "판매가", "요금세트", "WINGSCMS" | 판매가 변경 | `references/cms.md` |
| "예약이 안 들어온다", "판매가 멈췄다" | 정지 대응 | `references/suspension.md` |

**계산만 하면 되는 요청에 조사를 돌리지 마라.** 저장된 `property.json` 이나 프로필이 있으면 그 값으로 계산하고, 오래됐을 때만 익스트라넷을 연다.
단, **요금 답변 전에 소비자 페이지에서 예약 가능 여부는 본다.**

## 전체 흐름 (조사부터)

```
1. 사전 점검  로그인 · 숙소 ID · 프로필과 기준 문서 · 예약 가능 여부 확인
2. 숙소 점검  상태 · 숙소 페이지 점수 · 사진 · 후기 · 프로그램 · 요금제와 취소 정책 · 객실 · 검색 요인 · 기회 센터   references/audit.md
3. 측정      적용 중인 프로모션 → 중복 규칙 → 요금제 배수 → 판매가 → 최근 예약 결제·정산 → 소비자 페이지
4. 대조      소비자 페이지 값과 계산값을 원 단위로 비교, payout.py booking 으로 입금 계수 확인
5. 기록      property.json 작성 (점검 결과는 audit[])
6. 검사      build_console.py --check : 점검 위험 · 순서 제약 · 하한 · 원장 불일치 확인
7. 생성      build_console.py → HTML
8. 전달      파일 + 점검 위험 목록 + 측정값 표 + 못 읽은 것
```

## 시작 — 숙소 프로필을 먼저 확정한다

1. 작업 폴더나 이 스킬 폴더에 `hotel-profile.md` 가 있으면 읽는다.
2. 없으면 `hotel-profile.example.md` 양식의 항목을 사용자에게 받거나, 익스트라넷·CMS 화면에서 읽어 채운다.
3. **프로필에 없는 값은 지어내지 않는다.** 본문과 양식의 숫자는 형식 예시다 — 다른 숙소의 값을 복사하지 마라.

계산에 반드시 필요한 것: 판매가(요금세트별) · 요금제 배수 · 기준 인원과 인원 계수 ·
타겟 요금 할인율 · 포트폴리오형 할인율 · 캠페인 · **입금 계수(실예약으로 역산한 값)** · 입금가 하한.
하나라도 없으면 그 항목을 "미확인"으로 표시하고, 그 값이 필요한 계산은 확정값이라고 쓰지 않는다.

## 공식 요약

```
기존 요금 = 판매가 × 요금제 배수 × 인원 계수 × (1 − 타겟 요금)
노출가    = 기존 요금 × (1 − 포트폴리오형)
입금가    = 노출가 × 입금 계수              ← 반올림 전 노출가에 곱한다
인원 계수  = 1 − 감액폭 × 기준 인원과의 차이    ← 곱셈이 아니라 뺄셈
역산     = 목표 ÷ (요금제 × 인원 × (1 − 타겟) × (1 − 포트폴리오) × 입금 계수) → 100원 올림
```

- **단계 사이는 곱셈이고, 같은 카테고리 안에서는 큰 할인 하나만 걸린다.**
- 캠페인과 집중형 특가는 숙소의 조합을 대체한다. 큰 쪽 하나만 걸린다. Genius는 집중형 특가를 뺀 나머지에 더 곱해진다.
- 근거와 예외는 `references/pricing.md` 에 있다. 프로모션을 판단하기 전에 반드시 읽는다.

## 숙소를 어떻게 찾는가 — ID를 묻지 마라

로그인 뒤 열리는 주소의 `hotel_id=` 가 숙소 ID 이고, 상단 숙소명이 숙소 이름이다. 계정에 숙소가 하나면 묻지 말고 그 숙소로 시작한다.
여러 숙소 계정의 목록 화면은 이 스킬을 만들 때 확인하지 못했다. 처음 만나면 그 경로를 `portal-map.md` 에 적고, 이름을 받았으면 목록에서 맞춰 바로 시작한다.
**중간에 질문하지 마라.** 판단이 필요하면 스스로 정하고 무엇을 가정했는지 결과 보고에 적는다. 막힌 영역만 `null` + `open[]` 에 남기고 나머지를 끝까지 한다.
여러 숙소를 한 번에 시켰으면 숙소별로 `properties/{이름}-{ID}.json` 과 HTML 을 각각 만들고 마지막에 비교 표를 낸다.

## 측정할 때 지킬 것

- **화면에서 읽은 것만 적는다.** 모르는 값은 `null` 로 두고 `open[]` 에 "무엇을 어떻게 확인하나"를 적는다.
- **설정 가능 범위와 현재 설정을 섞지 않는다.** "1~40% 설정 가능, 현재 5%"는 두 개의 사실이다. `programs[].range` 와 `setting` 에 나눠 적는다.
- **결론이 뒤집히면 왜 바뀌었는지 남긴다.** `findings[].revised` 에 이전 판정과 정정 사유를 적는다.
- **노출가는 날짜 3개 이상으로 잰다** (`measurements[]`). 우리 요금(직판)만 넣고 재판매 값은 넣지 않는다.
- 투숙객 이름·연락처·예약번호, 담당자 연락처, 비밀번호·쿠키·토큰은 어디에도 적지 않는다.
- 저장·적용·참여·중지·삭제 버튼은 화면을 열어 두는 데까지만 하고 누르는 건 사용자에게 맡긴다(프로필의 버튼 정책이 따로 있으면 그것을 따른다).

## 조사를 마친 뒤

`findings[]` 가 결론이다. 심각도 순으로 정렬하고 각 항목에 **근거**를 붙인다. "사진 태그 2장 누락"은 실측이고 "객실 사진부터 처리"는 판단이다. 둘을 같은 문장에 넣지 않는다.
새로 조사한 숙소는 `properties/{이름}-{ID}.json` (과 프로필 `.md`)으로 남긴다. 다음 계산 요청이 빨라진다. 스킬 폴더에 쓸 수 없으면 사용자의 작업 폴더에 같은 이름으로 저장하고 위치를 알린다.
끝나면 반드시 이 셋을 낸다: ① `SendUserFile` 로 HTML (사용자가 계속 볼 물건이면 Artifact 로도 게시) ② 측정값 표(값마다 화면·자료 출처) ③ 못 읽은 것과 그 이유.

## 계산기

```
python scripts/payout.py forward --rate 200000 --plan 0.95 --target 25 --portfolio 20 --k 0.82 --floor 90000
python scripts/payout.py reverse --target-payout 90000 --plan 0.95 --target 25 --portfolio 20 --k 0.82
python scripts/payout.py check   --rate 200000 --plan 0.95 --target 25 --portfolio 20 --add 3 5 --k 0.82 --floor 90000
python scripts/payout.py restore --original 142500 --plan 0.95 --target 25
python scripts/payout.py booking --shown 114000 --payout 93480
python scripts/payout.py cells   --property property.json --room 스탠다드 --set WEEK --plan Non-refundable
python scripts/payout.py floor   --property property.json
```

위 숫자는 형식 예시다. 인원 계수는 `--occ`, 판매가 올림 단위는 `--unit` 이다.

## 콘솔 만들기

`assets/property.example.json` 을 복사해 값을 채운다. `_note` 에 칸마다 쓰는 법이 있다.

```
python scripts/build_console.py property.json --check
python scripts/build_console.py property.json -o 콘솔.html
```

콘솔은 아고다 콘솔과 같은 네 화면(현재 설정 · 계산기 · 요금표 · 실측 기록)을 탭으로 나눈다. 「현재 설정」 맨 위에 요약과 발견 사항(심각도 순)이 오고, 점검 결과, 프로그램(설정 가능 범위 · 현재 설정), 콘텐츠(사진 · 리뷰 · 매핑), 요금제, 노출가 실측이 이어진다. 「계산기」에는 아고다 계산기처럼 중복 규칙을 강제하는 프로모션 조합기와 수수료 조합 비교(`promoGroups` · `commissionParts`)가 붙는다. 조합기는 두 방향(요금 → 입금가, 목표 입금가 → 필요 요금)으로 돌고, 목표 칩(`targets`), 실측 비율 고정 토글(`measurements`), 요일·요금세트별 일괄 표(`rooms[].rates`), 할인·수수료·입금 분해 막대를 갖는다. 아고다 계산기처럼 항목별 할인율 직접 수정, 수수료 슬라이더(`range`)와 켜기/끄기, 올림 단위 전환(100·1,000·5,000원), 금액 단계 분해와 입금계수, 실측 점별 이론값 대조, 요일별 표의 하한 판정(하한 미달 · 턱걸이 · OK)과 필요 요금, 요금 칩(`property.ratePresets` 또는 객실 요금)도 있다. 탭은 주소의 `#p0~#p3` 으로 기억된다. 「요금표」에는 채널별 요금 비교(`channels`)가 붙는다. 그 뒤에 계수, 계산기, 리드타임별 입금가, 객실별 최심 칸과 하한 판정, 프로모션, 실측 원장, 미확인 항목이 들어간다. 값이 없는 카드는 자동으로 빠진다.
`--check` 는 아고다 스킬처럼 발견 사항의 근거 누락, 미확인 프로그램의 보고 누락, 예약 0건 요금제, 노출가 실측 비율 어긋남도 잡는다. 또 `verified:false` 가 붙은 모든 칸(묶음 `verified{}` 포함)이 findings·open 에 흔적을 남겼는지, 필수 영역(rooms · measurements · programs · content · ratePlans · findings)이 비었는지, 실측 비율이 범위를 벗어났는지, 최악 조합에서 하한을 지키려면 요금이 얼마여야 하는지 알린다. `--artifact` 를 붙이면 claude.ai Artifact 에 붙일 조각(`-artifact.html`)도 함께 만든다. 점검 위험·순서 제약·하한·원장 불일치는 요청받지 않았어도 보고한다.

## 절대 규칙

1. **로그인은 사용자가 직접 한다.** 비밀번호를 절대 입력하지 않는다. 세션이 풀리면 재로그인을 요청한다.
2. **저장·적용 버튼은 프로필의 「버튼 정책」을 따른다.** "에이전트가 끝까지 누른다"로 돼 있으면 변경 지시를 받은 범위에서 불가능한 것만 빼고 실행한다. 기록이 없으면 저장 직전에 멈추고 사용자에게 맡긴다.
3. **설정 화면만 보고 「됐다」고 하지 않는다.** 항상 소비자 페이지에서 역산해 확인한다.
4. **매 턴마다** 확인·판정·계산을 사용자가 지정한 작업 문서에 기록한다. (지정이 없으면 어디에 남길지 한 번 묻는다.)
5. **프로필의 입금가 하한**을 뚫는 변경은 하지 않는다. 뚫릴 것 같으면 먼저 계산해서 보고한다.
6. **부킹 채널만** 담당한다. 다른 채널은 비교 근거로만 쓴다.
7. 예약·투숙객의 이름·연락처·예약번호는 결과물과 기록에 넣지 않는다.
8. **요금 답변 전에 소비자 페이지에서 예약 가능 여부부터 본다** (`references/suspension.md`). 확인할 도구가 없으면 "예약 가능 여부 미확인"이라고 쓴다.

## 출력과 기록

결과는 항상 이 순서로 낸다.

1. **현재 설정표** — 프로필 기준 + 화면에서 다시 읽은 값 (다르면 표시)
2. **계산표** — 칸별(요금제 × 리드타임 × 회원 × 접속) 노출가 / 입금가 / 하한 대비 여유
3. **실측 대조** — 소비자 페이지 「기존 요금」「표시 요금」과 계산값, 차이
4. **변경 목록** — 화면에서 무엇을 몇 %로 고칠지, 변경 전 값, 되돌리기 절차
5. **미확인 항목** — 근거 없이 쓴 값이 무엇인지

기록은 사용자가 지정한 작업 문서에 남긴다. 시간순 로그에는 **폐기된 판정을 지우지 말고 「폐기」 표시와 정정 사유**를 남긴다 —
다음 세션이 오답을 물려받지 않게 하기 위해서다. 운영 중 새로 밟은 함정은 프로필의 「함정 메모」에 추가한다.
