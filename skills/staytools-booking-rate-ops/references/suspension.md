# 판매 정지 대응

예약 가능 여부 판정은 `scripts/snippets.js` 의 `__availability` 로 한다.


## 판매 정지 대응

**요금 질문에 답하기 전에 예약 가능 여부부터 본다.** 기록만 보고 할인율 표를 읊으면 판매가 멈춘 것을 놓친다.

```js
({ nameOK: document.body.innerText.includes('{프로필의 숙소명}'),   // false면 URL 오류. 정지로 판정하지 않는다
   blocked: /예약하실 수 없습니다|현재 저희 사이트에서/.test(document.body.innerText),
   rows: document.querySelectorAll('#hprt-table tr').length })
```
`nameOK` 가 true이고 `blocked` 가 true이거나 `rows` 가 0이면 판매 중단이다. 이때는 요금 답변보다 **판매 중단 사실을 먼저** 보고한다.
숙소 주소는 추측하지 말고 프로필이나 익스트라넷에서 가져온다.

1. **원인은 인박스 원문으로 확인한다.** 설정 화면보다 메시지 인박스를 먼저 연다.
   정지 전에 독촉 → 최후통첩 → 정지 통보가 날짜와 함께 남는다. 최후통첩의 마감일이 정지 시점의 확정 근거다.
2. **트리거와 현재 걸림돌을 나눠 쓴다.** 정지를 일으킨 것과 지금 정지를 유지시키는 것은 다를 수 있다.
   인과를 주장하면 시간순부터 본다 — 원인의 발효 시점이 정지보다 앞서야 한다. 독촉 날짜보다 늦게 발행된 청구서는 그 독촉의 대상이 아니다.
3. **청구서는 건별 상태로 기록한다.** 총액 한 줄로 적지 않는다. 번호 · 발행일 · 대상 기간 · 기한 · 상태 · 금액을 작업 문서에 적는다.
   「처리 중」은 납부 접수 상태이고, 「기한 경과」가 실제 위험 신호다.
4. **납부 후 재오픈은 자동이 아니다.** 부킹 공식 안내 순서는 이렇다.
   모든 미납 청구서 납부 → 부킹의 납부 확인 대기(최대 7일) → 상태가 「닫힘 - 재오픈 준비」로 변경 → **「내 숙소 오픈하기」를 직접 눌러야** 예약 접수 재개.
   납부일과 재개일은 다르다. 상태를 끝까지 추적한다.

납부는 사용자가 직접 한다.
