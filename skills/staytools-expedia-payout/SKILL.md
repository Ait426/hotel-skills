# 익스피디아 — 조사 · 계산 · 콘솔

**이 배포본에는 특정 숙소의 값이 없다.** 숙소 ID(htid = propertyId)·요율·프로모션·목표는 전부 그 숙소의 자료에서 온다.
`properties/example-hotel-00000000.json` 은 형식을 보여 주는 **가상 숙소**다. 그 숫자를 다른 숙소 계산에 쓰지 마라.

## 인자 처리 — 이게 최우선이다

숙소 ID(숫자)만 받고 호출되면 **묻지 말고 전체 흐름을 끝까지 돌려라.** 사전 점검 → 측정 → 공식 대조 → property.json → HTML → 전달까지다.

```
/staytools-expedia-payout                  로그인된 계정의 숙소를 찾아 조사 → HTML
/staytools-expedia-payout 12345678         그 숙소를 조사 → HTML
/staytools-expedia-payout 샘플 스테이        이름으로 찾아 조사 → HTML
/staytools-expedia-payout 12345678 계산만   조사 없이 저장된 값으로 계산
```

- 숙소를 찾을 때는 로그인된 파트너센트럴 주소의 `htid` 값과 화면의 숙소 선택기를 본다. 숙소가 여럿이고 이름도 없으면 목록을 보여 주고 고르게 한다.
- 로그인이 안 되어 있으면 사용자에게 요청하고 기다린다. 대신 로그인하지 마라.
- 막힌 영역은 `null` 과 `open[]` 에 남기고 나머지를 끝까지 진행한다. 한 영역 실패로 멈추지 마라.
- 목표 입금가처럼 **사용자만 정할 수 있는 값**은 지어내지 않는다. 없으면 비워 두고 보고에 적는다.

### 브라우저 도구가 없을 때 — 자료를 받아서 진행한다

포털을 읽을 도구가 없으면 조사를 지어내지 마라. 사용자가 준 자료(화면에서 옮긴 값, 엑셀·CSV, 예약 결제 내역)로 `property.json` 을 채워 계산과 HTML 생성까지 한다.

**최소 입력:** 숙소명 · 숙소 ID · 기본 보수율 · 엑셀러레이터 요율 · 객실별 달력요금 · 프로모션 목록(조건, 비회원/회원 할인율).
세금 배수를 받지 못하면 1.1을 넣고 `verified.T` 를 false 로 둔 뒤 `open[]` 에 확인 방법을 적는다.

끝나면 반드시 이 셋을 낸다.
1. HTML 파일 (전달 도구가 없으면 저장 경로)
2. 측정값 표 (각 값이 어느 화면·자료에서 나왔는지 포함)
3. 못 읽은 것과 그 이유

## 먼저 — 무슨 요청인지 가른다

| 사용자가 말한 것 | 할 일 | 읽을 것 |
|---|---|---|
| "입금가 얼마", "요금 얼마로 올려야 하나", "이 프로모션 켜도 되나" | 계산만 | `references/pricing.md` → `scripts/payout.py` |
| "실측했어?", "입금가가 이상하다" | 실측 대조 | `references/measure.md` → `payout.py booking` |
| "점검해줘", "현황 봐줘", "뭐가 부족해", "숙소 조사해줘" | 점검 + 조사 + 콘솔 | `references/audit.md` → `references/portal-map.md` → 아래 전체 흐름 |
| "노출 순위", "상품 강도", "고객 경험 점수", "요금 경쟁력", "후기" | 점검만 | `references/audit.md` |
| "콘솔 만들어줘", "계산기 만들어줘" | 생성 | `assets/property.example.json` → `scripts/build_console.py` |
| "요금세트", "예약이 안 들어온다" | 운영 점검 | `references/cms.md` |

**계산만 하면 되는 요청에 조사를 돌리지 마라.** 저장된 `property.json` 이나 프로필이 있으면 그 값으로 계산하고, 오래됐을 때만 포털을 연다.

## 전체 흐름 (조사부터)

```
1. 사전 점검  로그인 · 숙소 ID · 프로필과 기준 문서 확인
2. 숙소 점검  노출 순위 요인 · 요금 경쟁력 · 세부 정보와 객실 설명 · 후기 · 프로그램 · 객실과 취소 정책 · 기회   references/audit.md
3. 측정      최근 예약 결제 내역 → 프로모션 수정 화면 → 달력요금 → 고객페이지
4. 대조      payout.py booking 으로 공식과 실입금 비교 (오차 1원 이내)
5. 기록      property.json 작성 (점검 결과는 audit[])
6. 검사      build_console.py --check : 점검 위험 · 빈 구간 · 원장 불일치 확인
7. 생성      build_console.py → HTML
8. 전달      파일 + 점검 위험 목록 + 측정값 표 + 못 읽은 것
```

## 시작하기 전에 반드시 할 것 세 가지

### 0) 숙소 프로필을 확정하라

작업 폴더나 이 스킬 폴더에 `hotel-profile.md` 가 있으면 읽는다. 없으면 `hotel-profile.example.md` 양식의 항목을
사용자에게 받거나 파트너센트럴 화면에서 읽어 채운다. **프로필에 없는 값은 지어내지 않는다.**
본문과 양식의 숫자는 형식 예시다 — 다른 숙소의 요율·프로모션을 복사하지 마라.

### 1) 숙소의 기준 문서를 먼저 읽어라

프로필의 「기준 문서」에 적힌 문서(요금 설계 정본, 문서 점검 대장)가 있으면 그것부터 읽는다.
운영 문서가 쌓이면 **상당수가 폐기됐는데도 미완료 지시서 형태로 남는다.**
점검 대장을 안 보고 옛 문서를 실행하면 **살아 있는 프로모션을 중지시키거나 중복 생성한다.**
기준 문서가 없는 숙소면 이번 작업의 결과를 첫 기준 문서로 남긴다.

### 2) 계수를 오늘 값으로 확인하라

**입금 계수는 고정이 아니다.** 엑셀러레이터 요율이 바뀌면 같이 바뀐다.
최근 예약 1건의 결제 내역에서 `Accelerator (n%)`를 읽는 것이 가장 빠르다 (`references/measure.md`).

## 공식 요약

```
입금 계수 k = T × (1 − c) − a
입금가     = 달력 ÷ T × (1 − d) × k
역산 달력   = 목표입금가 × T ÷ (k × (1 − d))
패키지 경로 = 달력 × p 를 달력 자리에 넣는다
```

- **할인은 덧셈이다.** 1층은 조건을 만족하는 것 중 가장 깊은 하나, 2층은 회원 가산이다. 2층끼리는 쌓이지 않는다.
- `c` 는 세금 포함 결제 총액, `a` 는 할인 후 세전 기준이다. 그냥 더하면 틀린다.
- 근거와 예외는 `references/pricing.md` 에 있다. 프로모션을 판단하기 전에 반드시 읽는다.

## 숙소를 어떻게 찾는가 — ID를 묻지 마라

로그인 뒤 주소의 `htid=` 또는 `propertyId=` 가 숙소 ID 다. 계정에 숙소가 하나면 묻지 말고 그 숙소로 시작한다.
여러 숙소 계정의 숙소 선택 화면은 이 스킬을 만들 때 확인하지 못했다. 처음 만나면 그 경로를 `portal-map.md` 에 적고, 이름을 받았으면 목록에서 맞춰 바로 시작한다.
**중간에 질문하지 마라.** 판단이 필요하면 스스로 정하고 무엇을 가정했는지 결과 보고에 적는다. 막힌 영역만 `null` + `open[]` 에 남기고 나머지를 끝까지 한다.
여러 숙소를 한 번에 시켰으면 숙소별로 `properties/{이름}-{ID}.json` 과 HTML 을 각각 만들고 마지막에 비교 표를 낸다.

## 측정할 때 지킬 것

- **화면에서 읽은 것만 적는다.** 모르는 값은 `null` 로 두고 `open[]` 에 "무엇을 어떻게 확인하나"를 적는다.
- **설정 가능 범위와 현재 설정을 섞지 않는다.** "1~40% 설정 가능, 현재 5%"는 두 개의 사실이다. `programs[].range` 와 `setting` 에 나눠 적는다.
- **결론이 뒤집히면 왜 바뀌었는지 남긴다.** `findings[].revised` 에 이전 판정과 정정 사유를 적는다.
- **노출가는 날짜 3개 이상으로 잰다** (`measurements[]`). 우리 요금(직판)만 넣고 재판매 값은 넣지 않는다.
- 투숙객 이름·연락처·예약번호, 담당자 연락처, 비밀번호·쿠키·토큰은 어디에도 적지 않는다.
- 저장·적용·참여·중지·삭제 버튼은 화면을 열어 두는 데까지만 하고 누르는 건 사용자에게 맡긴다(프로필의 버튼 정책이 따로 있으면 그것을 따른다).

## 조사를 마친 뒤

`findings[]` 가 결론이다. 심각도 순으로 정렬하고 각 항목에 **근거**를 붙인다. "사진 태그 2장 누락"은 실측이고 "객실 사진부터 처리"는 판단이다. 둘을 같은 문장에 넣지 않는다.
새로 조사한 숙소는 `properties/{이름}-{ID}.json` (과 프로필 `.md`)으로 남긴다. 다음 계산 요청이 빨라진다. 스킬 폴더에 쓸 수 없으면 사용자의 작업 폴더에 같은 이름으로 저장하고 위치를 알린다.
끝나면 반드시 이 셋을 낸다: ① `SendUserFile` 로 HTML (사용자가 계속 볼 물건이면 Artifact 로도 게시) ② 측정값 표(값마다 화면·자료 출처) ③ 못 읽은 것과 그 이유.

## 계산기

```
python scripts/payout.py forward --rate 165000 --discount 20 10 --c 15 --a 5 --floor 90000
python scripts/payout.py reverse --target 92925 --discount 30 --c 15 --a 5
python scripts/payout.py check   --rate 165000 --discount 30 --add 3 7 --c 15 --a 5 --floor 90000
python scripts/payout.py table   --c 15 --a 5 --targets 82000 90000
python scripts/payout.py coef    --c 15 --rates 0 1 5 7
python scripts/payout.py booking --after 105000 --paid 115500 --comp 17325 --accel 5250 --payout 92925
python scripts/payout.py leadmap --property property.json
```

위 숫자는 형식 예시다. 패키지 경로는 `--p` 를 더한다. 세금 배수는 `--t` 이고 기본은 1.1이다.

## 콘솔 만들기

`assets/property.example.json` 을 복사해 값을 채운다. `_note` 에 칸마다 쓰는 법이 있다.

```
python scripts/build_console.py property.json --check
python scripts/build_console.py property.json -o 콘솔.html
```

콘솔은 아고다 콘솔과 같은 네 화면(현재 설정 · 계산기 · 요금표 · 실측 기록)을 탭으로 나눈다. 「현재 설정」 맨 위에 요약과 발견 사항(심각도 순)이 오고, 점검 결과, 프로그램(설정 가능 범위 · 현재 설정), 콘텐츠(사진 · 리뷰 · 매핑), 요금제, 노출가 실측이 이어진다. 그 뒤에 계수, 계산기, 리드타임별 입금가와 목표 판정, 프로모션, 실측 원장, 미확인 항목이 들어간다. 값이 없는 카드는 자동으로 빠진다.
`--check` 는 아고다 스킬처럼 발견 사항의 근거 누락, 미확인 프로그램의 보고 누락, 예약 0건 요금제, 노출가 실측 비율 어긋남도 잡는다. 점검 위험·빈 구간·원장 불일치는 요청받지 않았어도 보고한다.

## 작업 순서

### 계산할 때
1. 최근 예약 1건으로 **현재 엑셀러레이터 요율**을 확인해 계수를 확정한다 (확인 못 하면 프로필 값을 쓰고 "미확인 요율"이라고 표시)
2. 그 구간에 걸리는 **1층 최댓값 + 2층**을 구한다 (프로모션 개수를 세지 말고 가장 깊은 것을 찾아라)
3. 공식에 넣는다. 목표에서 역산할 때는 **일반 할인 하한**을 먼저 확인한다
4. 역산한 달력요금은 **올림**한다(반올림하면 목표에 몇 원 못 미칠 수 있다). 달력은 리드타임 공통 값이므로,
   한 구간 때문에 달력을 올리면 **다른 구간의 손님 결제액도 같이 오른다** — 그 변화도 같이 적는다

### 프로모션을 켜고 끌지 판단할 때
1. 그 프로모션을 켜면 그 구간의 **1층 최댓값**이 바뀌는가
2. 바뀐다면 입금가가 목표선을 넘는가
3. 안 넘으면 → 달력을 얼마로 올려야 하는지 역산해서 같이 제시

**프로모션만 켜라고 하고 달력 이야기를 빼면 사고가 난다.**

### 요금을 바꿀 때 — 달력 먼저, 프로모션 나중

| 순서 | 사이 구간 | 손실 |
|---|---|---|
| 프로모션 먼저 | 옛 달력에 새(깊은) 할인 | 🔴 **헐값 판매. 돈이 나간다** |
| **달력 먼저** | 새 달력에 옛(얕은) 할인 | 🟡 잠깐 비싸다. **손실 없음** |

되돌릴 때는 반대 순서다.

### 검증할 때 — 6층까지 가야 확정이다

```
1층 CMS 재조회 → 2층 프로모션 수정화면 재확인 → 3층 고객페이지 날짜별
→ 4층 전수(판매 기간 × 전 객실) → 5층 24시간 뒤 반복 → 6층 실예약 결제 내역
```

**화면값끼리의 대조는 아직 화면값이다.**

## 버튼 정책 — 프로필을 따른다

숙소마다 다르다. 프로필의 「버튼 정책」에 적힌 대로 한다. **기록이 없으면 저장·제출 직전에 멈추고 사용자에게 맡긴다.**

프로필이 "에이전트가 저장까지 누른다"인 숙소에서는:
- 저장·적용·중지·제출을 **직접 누른다.** 매번 확인받지 않는다.
- **로그인만 사용자가 한다.** 자격 증명은 절대 입력하지 않는다.
- 대신 **누르기 전 검증을 더 엄격하게 한다** — 바꾼 행뿐 아니라 안 바꾼 행까지 기대값과 대조하고, 저장 후 화면을 이탈했다 돌아와 서버에서 다시 읽는다.
- **롤백값은 누르기 전에 문서에 적는다.**

버튼 정책이 바뀐 적이 있으면 옛 문서의 반대 규칙은 **폐기된 규칙**이다. 프로필이 기준이다.

---

## 🔴 폐기된 문서 — 그대로 실행하면 사고가 난다

운영 문서가 쌓인 숙소에서는 작업 전에 **문서 점검 대장**을 만든다(없으면 이번에 만든다). 이런 문서가 위험하다.

| 유형 | 위험 |
|---|---|
| 실행된 적 없는 설계안이 최신 버전 번호를 달고 있음 | 중지 목록에 **살아 있는 프로모션**이 들어 있을 수 있다 |
| 이미 완료된 실행 체크리스트 | 재실행하면 프로모션이 **중복 생성**된다 |
| 이전 버전의 작업 지시서 | 따라가면 현행 위에 옛 프로모션이 중복 생성되고 요율이 되돌아간다 |
| 「확정」이라는 제목이 붙은 옛 요율표 | 현행으로 오독된다 |
| 옛 엑셀러레이터 요율로 계산한 실측·역산 문서 | 그 계수로 만든 역산 달력을 그대로 쓰면 몇 % 싸게 팔린다 |
| 이미 해소된 문제의 조사 문서 · `판정필요` 태그 | 열린 과제로 보이게 한다 |

대장에는 문서마다 **현행 / 폐기 / 완료** 상태와 "살릴 것"을 적는다.

## 지켜야 할 선 — 프로필에서 읽는다

- 리드타임 구간별 목표 입금가 (어느 손님 기준인지: 자국 POS 회원 등)
- 요일·객실별 목표가 따로 있으면 그것
- 운영자가 직접 관리하는 요금세트 (미리 걸지 않는다)
- 담당 범위는 **익스피디아 단독**. 다른 채널은 비교 근거로만 쓴다
- 다른 채널의 계수를 익스에 쓰지 마라. **채널마다 다르다**

목표가 프로필에 없으면 계산 결과만 내고 "목표 미지정"이라고 밝힌다. 목표를 지어내지 않는다.

## 사실만 말하기

- **실측값과 계산값을 반드시 구분해서 쓴다.** 고객페이지 숫자에 계수를 곱한 것은 계산값이다
- **표본이 1이면 「1건에서는 이랬다」라고만 쓴다.** 1건으로 「패키지는 요율이 다르다」고 단정했다가 틀린 적이 있다
- **한 구간만 틀렸다면 요금표가 아니라 프로모션을 의심하라.** 요금표가 틀리면 전 구간이 틀린다
- 숫자가 안 맞으면 모델을 의심하기 전에 **입력(달력요금, 프로모션 목록)을 다시 읽어라**
- **매 턴 문서를 남긴다.** 그 턴에서 확인·판정·계산한 것을 프로필의 「기록 위치」에 기록한다
- 예약번호·투숙객 이름·연락처는 결과물과 기록에 남기지 않는다

## 출력 형식

1. **확인한 자료와 시점** — 프로필 / 화면 / 예약 결제 내역 중 무엇을 봤는지
2. **계수** — T · c · a · k, 각각의 근거(실측/프로필/미확인)
3. **리드타임별 표** — 구간 × (자국 POS/그 외) × (회원/비회원): 적용 할인 · 손님 결제 · 입금가(계산값) · 목표 대비.
   **경로 주의** 열을 넣는다: 직판 `(S)` / 패키지·B2B `(P)` 중 어느 경로의 값인지, `(P)` 실효 할인, 물량이 몰린 경로, 더 깊은 POS 프로모션에 덮이는지
4. **실예약 대조** — 실측 원장 형식
5. **변경 목록** — 무엇을 어떤 순서로(달력 먼저) 바꾸는지, 변경 전 값, 롤백 순서
6. **미확인 조건**
