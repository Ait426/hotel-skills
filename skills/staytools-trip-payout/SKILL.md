# 트립닷컴 입금가 · 요금 설계

**이 배포본에는 특정 숙소의 값이 없다.** 숙소 ID·수수료율·프로모션·목표는 전부 「숙소 프로필」에서 온다.

## ★ 시작하기 전에 반드시 할 것 세 가지

### 0) 숙소 프로필을 확정하라

작업 폴더나 이 스킬 폴더에 `hotel-profile.md` 가 있으면 읽는다. 없으면 `hotel-profile.example.md` 양식의 항목을
사용자에게 받거나 eBooking 화면에서 읽어 채운다. **프로필에 없는 값은 지어내지 않는다.**
본문과 양식의 숫자는 형식 예시다 — 다른 숙소의 요율·프로모션을 복사하지 마라.

**이 스킬의 공식은 「판매가 입력」 요금 모드 전제다.** 프로필의 요금 모드가 판매가 입력이 아니면 공식을 쓰지 말고
「확인 필요」(아래 표)로 보고한다.

### 1) 숙소의 기준 문서를 먼저 읽어라

프로필의 「기준 문서」에 적힌 문서(현행 요금표, 문서 점검 대장)가 있으면 그것부터 읽는다.
운영 문서가 쌓이면 **옛 요금표가 「현행」 표시를 단 채로 남고, 해제한 프로모션이 살아 있는 것처럼 적혀 있다**(아래 「폐기된 문서」).
기준 문서가 없는 숙소면 이번 작업의 결과를 첫 기준 문서로 남긴다.

### 2) 계수를 오늘 값으로 확인하라

**프로모션 %는 고정이 아니다.** 입금가를 말하기 전에 세 곳을 본다.

| 볼 곳 | 위치 | 왜 |
|---|---|---|
| **OFF 칸** | My promotions의 할인 칸 (`nn% OFF`) | 프로모션 **이름의 %는 믿지 않는다.** 한 숙소 관측: 이름과 OFF 칸이 달랐다 |
| **Logs** | Details → Logs | 누가·언제·전후값이 찍힌다. 한 숙소 관측: 트립 담당자 계정이 캠페인·Package를 만들고, 호텔이 바꾼 값을 예고 없이 되돌렸다 |
| **최근 예약** | 예약 상세 지불 정보의 할인 내역 | 할인 ÷ 원래 객실 요금 비율로 OFF 칸을 검산한다 |

프로모션 목록 끝까지 봤다고 끝이 아니다. 조사 순서: My promotions → 프로모션 카탈로그 → 캠페인 탭 → 비즈니스 기회의 프로그램 → 마케팅 계정.

## 공식

기호: `r` 파생 배수(환불불가·인원별, 해당 없으면 1) · `c` 수수료율 · `Σ` 호텔 부담 할인 합계 · `A` 예약 지급액의 추가 항목

```
P'           = 기준 판매가 × r        ← 고객 페이지 취소선 정가
원래 객실 요금  = P' × (1 − c)          ← 예약 상세 「원래 객실 요금」(이미 수수료를 뗀 값)
최종 객실 요금  = 원래 객실 요금 × (1 − Σ)
지급액         = 최종 객실 요금 − A      ← 예약 상세 「지급액」(입금의 정본)

역산:  기준 판매가 = 목표 ÷ (r × (1 − c) × (1 − 최저경로 Σ))   → 천원 단위 올림
복원:  P' = (실입금 + 할인 합계) ÷ (1 − c)      (추가 항목 A가 찍혀 있으면 A도 더한다)
```

- **할인은 곱셈이 아니라 덧셈이다.** 프로모션 40% + 회원 10% = 50%이지 46%가 아니다 (가상).
- **파생은 곱셈이다.** `r`은 판매가 단계에서 곱하고, 프로모션은 수수료 후 금액에 더해서 뺀다. 둘을 섞지 마라.
- **`A`는 예약 지급액에서 읽는다.** 비율을 공식으로 만들지 마라. 관측된 차감 비율은 예약마다 달랐다.
- **입금의 정본은 예약 지급액이다.** 위 식으로 낸 값은 계산값이다.
- 다른 채널의 계수를 트립에 쓰지 마라. **채널마다 다르다.**

### 계산 예시 (가상 숙소 — 형식만 본다)

기준 판매가 200,000 · r 0.9 · c 15% · Σ 50% (가상)
→ P' 180,000 → 원래 객실 요금 153,000 → 최종 객실 요금 76,500 → **지급액 76,500** (A = 0)
같은 예약에 A 3,000(가상)이 찍히면 → 지급액 73,500

역산 (가상): 목표 70,000 · r 0.9 · c 15% · 최저경로 Σ 50%
→ 70,000 ÷ (0.9 × 0.85 × 0.5) = 183,006.5 → **184,000** (검산 70,380)
반올림해서 183,000을 쓰면 69,997.5로 **목표 미달**이다. 그래서 올림한다.

복원 (가상): 실입금 76,500 + 할인 합계 76,500 = 153,000 → ÷ 0.85 = **P' 180,000** → ÷ r 0.9 = 기준 판매가 200,000

### 레버리지 — 같은 %p라도 Σ가 높을수록 비싸다

`입금 감소율 = 1 − (1 − Σ − Δ) ÷ (1 − Σ)`
예(가상): Δ 10%p는 Σ 20%에서 입금 −12.5%, Σ 50%에서 입금 −20%.

## 호텔 부담 vs 트립 부담

| 호텔 부담 — 입금에서 빠진다 | 트립 부담 — 입금과 무관 |
|---|---|
| 프로모션·캠페인 (상세에 「판매당 비용 계정으로 결제: 아니요」) | 신규회원 할인코드 |
| 회원 할인 TripPlus | 첫 예약 특가 |
| CoinPlus 등 프로그램 차감 (`A`) | 끝전 맞춤 |
| | 손님이 코인으로 결제한 금액 |

- 「판매당 비용 계정」으로 결제되는 항목은 미조사다. 「예」로 표시된 프로모션을 만나면 **미확인**으로 적는다.
- CoinPlus의 차감은 **손님에게 새로 적립되는 보너스 코인 값을 호텔이 내는 것**이고, 손님 결제가를 내리지 않는다.
- 트립 부담 항목을 구분한 근거: 한 숙소 관측으로 실예약 약 1,000건의 Promotion 칸에 「첫 예약」 류가 한 건도 없었다.

## Σ 산정 — 이 순서로 묻는다

```
유입 경로 → 적용 국가 → 대상 객실·요금제 → 회원 여부 → 프로그램 차감
```

| 순서 | 묻는 것 | 어디서 읽나 |
|---:|---|---|
| 1 | **어느 경로로 들어왔나** — Package 대상(트립에서 항공·기차·티켓 등을 예약한 손님)인가, 일반 검색인가, 연박(최소 숙박) 조건을 채웠나 | 예약 할인 내역 / 프로모션 Details |
| 2 | **그 손님 국가가 적용 목록에 있나** — 이름이 아니라 목록으로 판단 | Details 「적용 국가 및 지역」 |
| 3 | **그 객실·요금제가 대상인가** — 「전 객실」로 단정 금지 | Details 「Room types and rate plans」 |
| 4 | **회원인가** — 회원 가산 `m`을 더한다 (프로필의 값) | 예약 할인 내역, 프로그램 화면 |
| 5 | **프로그램 차감이 있나** — Σ가 아니라 `A`로 따로 뺀다 | 지불 정보 「추가 요금」 줄 |

한 숙소 관측: 같은 객실·같은 날짜가 경로에 따라 다른 지급액으로 들어왔다. 3번을 빼먹어 영향 규모를 몇 배 틀린 적도 있다.
어떤 프로모션의 대상이 아닌 객실은 그 손님에게 Σ가 `0` 또는 `m`까지 내려간다.

**겹치지 않는 할인끼리는 큰 쪽 하나만 걸린다. 비교는 「프로모션 + 회원」 합계로 한다.**
한 숙소 관측: 캠페인보다 얕은 기본 할인이 회원 가산을 더하자 캠페인보다 커져서 회원 예약의 입금을 깎았다.

## 프로모션 유형 · 중복 규칙

| 묶음 | 유형 | 메모 |
|---|---|---|
| 특정 그룹 | Mobile Rate · 항공+호텔 · XPOS | XPOS는 지역 지정 |
| 기본 | 기본 할인 · 사전 예약 · 라스트 미닛 · 연박 혜택 · 당일 밤 특가 · 객실 다량 예약 할인 | 당일 밤 특가에는 국적 구분이 없다 |
| 파격 특가 | 기간 한정 특가 | |
| 캠페인 | Country Banner 등 트립 마케팅 캠페인 | 기간·시장 한정, 최소 할인 15~20% (시점값, 다를 수 있음) |
| Package | 교통 예약 손님 | 수정 화면 설명 기준. 적용 국가 제한 없음으로 관측 |
| 프로그램 | TripPlus · CoinPlus · 특전 · Smart Offer 등 | 프로모션 화면 밖, 비즈니스 기회 메뉴 |

**중복 규칙은 외우지 말고 화면 원문을 읽는다.** 위치: 프로모션 > My promotions > Details > Modify >
「Discounts and stay dates」 아래 「Promotion stacking rules」. 유형마다 목록이 다르다.

| 기준 프로모션 | 겹침 | 안 겹침 (큰 쪽 하나만) |
|---|---|---|
| XPOS 화면 원문 | TripPlus, CoinPlus, Basic Deal, Early Bird, Last Minute, Offer for Tonight, Minimum Stay | Packages, campaigns, Mobile Rate |
| 연박 혜택 화면 원문 | TripPlus, CoinPlus, XPOS, 모바일 요금 | 패키지, 이벤트, 얼리버드, 라스트 미닛, 당일 특가, 기본 할인 |
| Package 수정 화면 | CoinPlus, TripPlus | 배너, XPOS |

(시점값, 다를 수 있음)

- 캠페인과 Package는 같이 붙지 않는다. 한 숙소 관측: 예약 650건 전수에서 공존 0건.
- 연박 혜택이 캠페인을 이기려면 캠페인보다 커야 한다. 작게 걸면 그 손님에게 효과가 없다.
- 깊은 연박 혜택에 회원 가산이 더해지면 최저 경로가 바뀐다. 한 숙소 관측: 실예약에서 연박 + 회원 합산을 확인했다.

### ★ 「확인 필요」 — 단정하지 말고 숙소별로 확인한다

| 항목 | 지금 아는 것 | 확인 방법 |
|---|---|---|
| **캠페인 + 회원 중복** | 프로모션 + 회원 합산은 확인됐다. 캠페인 + 회원은 한 숙소 관측으로 650건 중 4건뿐 공존(캠페인 단독 193건)이라 규칙이 안 풀렸다 | 예약 엑셀 Promotion 칸에서 캠페인이 찍힌 건의 회원 동반 여부를 세고, 동반 건의 할인 내역을 펼쳐 합이 더해졌는지 본다 |
| **프로모션 적용 기준 (IP / POS / 거주국)** | 화면에는 「적용 국가 및 지역」만 있다. 무엇으로 판별하는지 근거가 없다 | 트립에 문의한다. 답이 없으면 「손님 국가 미확인」으로 표시하고 실제 찍힌 할인으로만 말한다. 한국에서 조회한 화면으로 다른 국가 가격을 말하지 마라 |
| **항공+호텔과 Package의 관계** | Package의 대상 손님은 수정 화면 설명으로 확인됐다. 카탈로그의 「항공+호텔」 유형과 같은 것인지는 근거가 없다 | My promotions의 유형 표시와 카탈로그 항목을 대조하고, 안 풀리면 트립에 문의한다 |
| **회원 할인이 플랫폼 고정값인가** | 등급별 전부 10%로 관측 (시점값, 다를 수 있음). 화면에 수정 버튼이 있어 고정인지 불명 | TripPlus 화면에서 읽어 프로필에 적는다. 고정값으로 쓰지 않는다 |
| **넷가·후불·VCC 계약** | 미검증. 이 스킬의 공식은 판매가 입력·선결제에서만 확인됐다 | 재무 메인에서 결제 방식을, 요금제 목록에서 요금 모드를 읽는다. 다르면 실예약 지급액으로 공식을 새로 검증하기 전까지 계산값을 내지 않는다 |
| **부가세 처리** | 한 숙소 관측: 지불 정보의 부가가치세 줄이 지급액에 가감되지 않았다. 세금 규정 화면은 미조사 | 호텔 정보 › 세금 규정과 정산 명세서를 읽고 세무 담당자에게 확인한다 |
| **조식 1인 요금의 출처** | 고객 페이지에 우리 요금제에 없는 조식 1인이 뜬다. 후보는 호텔 정책의 조식 단가, 또는 Pricing per guest 규칙. 한 숙소 관측에서 두 후보가 같은 값을 내 구분되지 않았다 | Pricing per guest 규칙을 읽고, 두 후보의 값이 달라지는 날짜의 고객 페이지 정가를 비교한다. 값을 시험 삼아 바꾸지 않는다 |

## 켜기 · 끄기 판정

프로모션을 판단할 때는 **「무엇과 겹치나」보다 「무엇을 밀어내나」를 먼저** 계산한다.

1. 대상 손님별로 **지금 걸리는 Σ**를 적는다 (경로 × 국가 × 객실 × 회원)
2. 켰을 때 각 손님의 Σ가 바뀌는가. **회원 가산을 더한 값으로 비교**한다
3. **최저경로 Σ가 바뀌는가.** 바뀌면 역산 계수도 바뀐다
4. 객실마다 따로 본다. 모든 객실에 걸면 스위트·조식 요금제에도 똑같이 붙는다. 한 숙소 관측: 스위트 조식 연박 예약의 입금이 같은 방 1박보다 낮아졌다
5. 목표선을 넘는가. 안 넘으면 판매가를 얼마로 올려야 하는지 역산해 같이 제시한다

**프로모션만 켜라고 하고 판매가 이야기를 빼면 사고가 난다.** 끌 때도 같은 표로 본다.

프로그램 대시보드의 예약·매출은 귀속치이지 증분이 아니다. 효과를 단정하지 말고 비용과 귀속 건수만 준다.
숙소의 판단 기준(예: 손님 결제가를 못 내리는 부담은 끈다)이 있으면 프로필에서 읽는다.

## 요금제 · 파생 · 인원별

| 구분 | 어떻게 움직이나 | 어디서 확인 |
|---|---|---|
| 환불불가 파생 | 기준 요금제 × `r`. 상태·제한을 승계할 수 있다 | 요금제 목록의 파생 규칙 |
| 인원별 요금 | 객실 × 요금제별 규칙. `r`에 곱해 넣는다 | **Calendar → 「Pricing per guest」** (요금제 편집 화면에는 없다) |
| 조식 요금제 | 숙소가 정한 값. 프로필의 규칙을 따른다 | 달력 |
| 트립 생성 조식 `[FD]` | 우리 요금제 목록에 없다. 기준 요금제에 정액을 얹어 트립이 만든다 | 고객 페이지 |

- **「안 변한다」를 주장하려면 입력값이 다른 날짜 두 개 이상을 본다.** 한 숙소 관측: 주중만 봐서 고정값으로 적은 인원별 요금이 실제로는 비율이었다.
- **달력에 값이 있어도 팔리는 건 아니다.** 판매 토글을 같이 본다.
- 인원을 바꿔 검색한다. 한 숙소 관측: 성인 수에 따라 뜨는 요금제가 달라졌다.

### `[FD]` 조식

- 숙소가 끌 수 있는 스위치를 eBooking 안에서 찾지 못했다. 한 숙소 관측: 요금제·달력·패키지·Connectivity·호텔 정책·도움센터를 전수로 봤다.
- 찾다가 막히면 더 파지 말고 트립 문의로 넘긴다.
- 한 숙소 관측: 우리 조식 요금제가 `[FD]`보다 싸면 `[FD]`가 화면에서 사라졌고, 우리 조식을 판매 중지한 날에는 `[FD]`가 그 자리에 떴다.
- 구분: 우리 요금제 목록에 없고, 취소 기한이 우리 정책과 다르며, 가격이 「기준 요금제 + 정액」이다. 얹는 금액은 프로필에 적는다.
- 조식을 운영하지 않는 날에 `[FD]`가 뜨면 **못 주는 상품이 팔린다.** 호텔 정책의 조식 운영 요일 화면을 근거로 트립에 제기한다.

## 재판매 구분 — 화면에 뜬다고 우리 요금이 아니다

트립은 같은 객실·같은 식사 조건이면 **제일 싼 공급처 하나만** 보여 준다(한 숙소 관측). 다른 공급처 상품이 더 싸면 우리 요금은 **판매 중지가 아니라 화면에서 숨는다.**

**화면으로만 판별한다. 다른 채널 요금에서 재판매가를 계산하지 마라.** 그런 식은 원본 조사에서 실측과 어긋나 철회됐다.

| 판별 | 우리 요금 | 다른 공급처 |
|---|---|---|
| 요금 행 `data-exposure`의 `rm_taglist` | `AgentRoom` 없음 | `AgentRoom`, `POINTOFORDER` 있음 |
| 가격 툴팁 「요금 정보」 | 「특별 할인」 줄 있음 | 없음 |
| 취소선 정가 | 달력 판매가 × r 과 같음 | 다름 |
| 무료 취소 마감·기한 | 프로필의 취소 정책과 같음 | 다를 수 있음 |
| eBooking 요금제 목록 | 있음 | 없음 |

```js
// 고객 페이지 콘솔. 클래스 이름은 바뀔 수 있다 — 빈 결과면 판별 불가로 적는다
[...document.querySelectorAll('[class*="saleRoomItemBox__"]')].map((r,i)=>{
  const de=r.getAttribute('data-exposure')||'';
  const t=(r.innerText||'').replace(/\n+/g,' ~ ');
  return '['+i+'] '+(/AgentRoom/.test(de)?'AGENT ':'DIRECT')+' | '+(t.match(/[\d,]{6,}원/g)||[]).join(' / ');
}).join('\n')
```

**「할인율이 작은 상품」이 보이면 정가가 판매가가 아니라는 신호일 수 있다.** 우리 공식을 대지 말고 위 표로 먼저 가른다.
재판매 예약의 입금 기준은 미확인이다.

### 안 뜨는 이유는 세 갈래 — 먼저 나눈다

| 이유 | 판정 | 어떻게 가르나 |
|---|---|---|
| 저장 안 됨 | 문제 | eBooking 달력의 값 |
| 판매 중지·재고 없음·조건 불일치 | 설정 확인 | 달력 토글·재고, 취소 기한(당일 검색에 무료취소가 안 나갈 수 있다), 인원 수 |
| 다른 공급처에 밀림 | 문제 | 같은 칸의 다른 공급처 상품이 위 표로 판별됨 |

**1박과 2박 화면을 둘 다 연다.** 한 숙소 관측: 판매가 인상 뒤 1박 무료취소 칸만 밀렸고 2박은 그대로였다.

## ★ 입금가 확인 경로

| 고객 페이지에 뜨는 것 | 안 뜨는 것 |
|---|---|
| 취소선 정가 · 할인 줄 · 손님 결제 | 수수료 · 프로그램 차감 · **지급액** |

**예약 상세:** 예약 관리 → 예약 클릭 → 드로어의 **지불 정보** → 입금가 뷰

- 「원래 객실 요금」 = **수수료를 뗀 값**. 판매가로 읽으면 수수료가 0%로 보인다
- 「할인 +N」을 눌러야 줄별로 나온다. 펼치기 전에는 합계뿐이다
- 「추가 요금」 줄 = 프로그램 차감. 입금이 공식보다 낮으면 여기를 본다
- 「자세히 보기」 = 날짜별 명세. **다박 예약은 밤마다 스택이 다를 수 있어** 합계로 %를 역산하지 않는다

**"입금가"라고 쓰려면 여기까지 와야 한다.** 그 외는 계산값이다.

### 「입금가가 이상하다」 진단 순서

1. 예약 상세 할인 줄(또는 예약 엑셀 Promotion 칸)을 본다
2. 할인 합계 ÷ 원래 객실 요금으로 %를 확인한다
3. 복원 공식으로 P'를 구해 그 날짜의 달력값과 대조한다
4. **P'가 맞으면 요금 문제가 아니라 할인 문제다.** 고치는 곳이 다르다 (달력·채널 매니저 vs 프로모션)
5. 새 할인인지는 My promotions · 캠페인 탭(「수정」= 참여 중, 「지금 가입」= 미참여) · 비즈니스 기회를 본다

### 고객 페이지로 역산할 때 — 취소선 정가와 요금 정보 툴팁만 쓴다

가격 위에 마우스를 올리면 「요금 정보」가 열린다.

- 취소선 정가 = P' (달력 판매가 × r)
- 「특별 할인」 줄 ÷ 정가 = 호텔 쪽 Σ의 점검값. 프로필 Σ와 어긋나면 끝전 맞춤이나 다른 프로모션이 섞인 것이니 예약 지급액으로 확정한다
- 신규회원 코드·첫 예약 특가 줄은 트립 부담이다. **쿠폰을 뺀 가격에 (1 − c)를 곱하면 입금을 낮게 잡는다**

예(가상): 정가 200,000 → 특별 할인 −100,000 → 신규회원 코드 −10,000 → 손님 90,000
입금 계산값 = 100,000 × 0.85 = **85,000** (90,000 × 0.85 = 76,500 은 틀린 값)

**파란 판매 표시가에 고정 계수를 곱해 입금을 구하지 마라.** 한 숙소 관측: 표시가 ÷ 정가는 날짜·요금제·계정마다 흔들렸다.
조회 계정이 쿠폰 대상이면 일반 손님과 다른 값이 보인다.

### 실측 원장 — 이런 표로 남긴다

| 예약 | 예약일 | 경로 | 붙은 할인 | P' | 원래 객실 요금 | Σ | A | **지급액** | 공식 차이 |
|---|---|---|---|---:|---:|---:|---:|---:|---:|
| 예약 A (가상) | 당일 | 일반 | 프로모션 40 + 회원 10 | 180,000 | 153,000 | 50% | 0 | **76,500** | 0 |

예약번호와 투숙객 이름은 원장에 남기지 않는다. "예약 A/B"와 예약일로만 가리킨다.

## 변경 순서 · 검증 층위

### 계산할 때
1. OFF 칸·Logs·최근 예약으로 현재 값을 확인한다 (못 하면 프로필 값을 쓰고 "미확인"으로 표시)
2. 객실별로 Σ 산정 순서를 밟아 **경로 표**를 만든다
3. **최저경로 Σ로 역산**하고 천원 단위 올림한다. 판매가 하나가 전 경로를 같이 움직이므로 경로별로 따로 맞출 수 없다
4. 올린 판매가로 **다른 경로와 1박 손님의 결제가**가 어떻게 바뀌는지 같이 적고, 재판매에 밀릴 수 있으면 표시한다
5. 환불불가와 무료취소 목표를 동시에 받으면 파생 때문에 둘 다 정확히 못 맞춘다. 앵커 하나를 정하고 다른 쪽 결과를 보고한다

### 요금을 바꿀 때 — 판매가 먼저, 프로모션 나중

프로모션 변경은 고객 페이지에 바로 반영되는 것으로 관측됐다 (시점값, 다를 수 있음).

| 순서 | 사이 구간 | 손실 |
|---|---|---|
| 프로모션 먼저 | 옛 판매가에 새(깊은) 할인 | 🔴 **헐값 판매. 돈이 나간다** |
| **판매가 먼저** | 새 판매가에 옛(얕은) 할인 | 🟡 잠깐 비싸다. **손실 없음** |

되돌릴 때는 반대 순서다. **롤백값은 누르기 전에 적는다.** 값을 바꾼 뒤에는 그 값을 전제로 쓴 옛 문장을 검색해 같이 고친다.

### 검증할 때 — 6층까지 가야 확정이다

```
1층 eBooking 달력(값·판매 토글·재고) → 2층 My promotions OFF 칸·대상·Logs
→ 3층 고객 페이지 정가(객실 × 요금제 × 인원, 1박·2박, 금·토 포함)
→ 4층 안 뜬 것 M건과 그 이유 → 5층 며칠 뒤 Logs·OFF 칸 재확인 → 6층 실예약 지급액
```

**달력부터 본다.** 고객 페이지부터 보면 노출 로직·프로모션·다른 공급처가 섞여 원인을 못 가른다.
보고는 「일치 N건」으로 끝내지 말고 **「안 뜬 것 M건과 이유」**를 같이 낸다. 화면값끼리의 대조는 아직 화면값이다.

## 데이터 수집

**예약 엑셀이 정본이고, Promotion 칸에 예약 당시 호텔 부담 할인과 CoinPlus 차감이 남는다.** 사라진 과거 프로모션도 여기서 복원된다.

| 규칙 | 이유 |
|---|---|
| 예약일(OrderDate)로만 조회된다 | 「Check-in date」 필터가 보여도 0건이었다 (시점값, 다를 수 있음) |
| 투숙월 집계는 **앞 두 달을 덧붙여** 받고, 맨 앞 달의 해당 투숙이 0건인지 본다 | 예약일 자료는 「그 해에 잔 건」이 아니다 |
| 집계는 확인된 예약만. `Revised` 등 무효 상태는 뺀다 | 예약번호가 달라 중복 제거로 안 걸러진다 |
| 건수는 **CSV 파서로** 센다. `wc -l` 금지 | 칸 안에 줄바꿈이 있다 |
| 한 건 받고 **파일이 생겼는지 확인한 뒤** 다음 건 | 연타하면 브라우저가 사이트 다운로드를 차단하고 에러가 안 뜬다 |
| 「다운로드」는 다운로드 목록에 작업을 만든다. 거기서 행별로 다시 받는다 | 성공 판정은 새 탭이 열렸나, 파일이 생겼나 |
| 파일명에 기간이 없다. 받자마자 이름을 바꾼다 | 작업 시각을 적어 두면 파일명 시각과 맞춰 볼 수 있다 |
| 날짜 범위는 URL 해시(`#filterType=OrderDate&dateValues[0]=…&dateValues[1]=…`)로 지정된다 | 날짜 선택기에 타이핑이 안 먹었다 (시점값, 다를 수 있음) |
| 예약 목록 API(`queryOrderList`)는 `total` 건수만 믿는다 | 오래된 달의 레코드가 에러 없이 빠졌다 |
| 국적 칸이 없다. 이름으로 추정하면 반드시 「추정」이라 쓴다 | 오차가 있다 |

요약 문서가 아니라 **독립적으로 받은 원본끼리** 대조한다. 작은 불일치를 반올림하지 마라.

| 프로모션 수정 화면에서 「Back」을 누르면 목록으로 나간다 | 한 페이지 세로 스크롤이다. 아래로 내린다 |
| 할인율 칸에 값이 안 먹는다 | React 칸. 네이티브 setter + input·change 이벤트, DOM값과 React값을 둘 다 대조. 하단 요약이 새 %로 바뀌었는지 확인 |
| 모달이 늦게 뜬다 (15~20초, 시점값, 다를 수 있음) | 화면이 어두워졌으면 눌린 것이다. 다른 데를 누르면 작업이 취소된다 |
| 해제는 여러 단계다: Deactivate → Confirm → 사유 선택 → Deactivate | 중간의 트래픽 감소 수치는 숙소 실적이 아니라 일반 문구로 관측됐다 |
| 고객 페이지에서 `document.body.innerText`가 차단될 때가 있다 | 페이지 텍스트 도구로 읽는다 |
| 연박 검색 목록의 마지막 금액을 박당가로 읽는다 | 「총금액」 앞에서 자른다 |
| 달력 아래쪽 객실이 안 읽힌다 | 스크롤해 lazy-load 시킨 뒤 읽고, 날짜 헤더로 열을 먼저 잡는다 |
| 프로그램 대시보드의 기간 값이 서로 모순된다 | 기간 수치로 추세를 읽지 말고 예약 단위 차감액을 본다 |
| 로그인 여부를 없는 페이지에서 판정 | 로그인이 필요한 실제 화면(My promotions 등)으로 판정 |
| 메시지·문의 채팅창이 열렸다 | 타이핑하지 않는다. 문의 발송은 사용자가 정한다 |

## 버튼 정책 — 사용자가 누른다

- **로그인·결제·최종 저장은 사용자가 한다.** 자격 증명은 절대 입력하지 않는다.
- 스킬은 변경 내용과 롤백값을 정리하고 **저장·적용·중지·제출·약관 동의 직전에 멈춘다.**
- 누르기 전 검증을 엄격하게 한다 — 바꾼 행뿐 아니라 안 바꾼 행까지 기대값과 대조한다.
- 사용자가 누른 뒤 화면을 이탈했다 돌아와 서버 값을 다시 읽는다.

프로모션 수정의 「Promotion Agreement」 동의 체크, 리뷰 신고 같은 제출, 트립 문의 발송도 사용자가 한다.

## 🔴 폐기된 문서 — 그대로 실행하면 사고가 난다

운영 문서가 쌓인 숙소에서는 작업 전에 **문서 점검 대장**을 만든다(없으면 이번에 만든다). 이런 문서가 위험하다.

| 유형 | 위험 |
|---|---|
| 옛 요금표가 「현행」·「확정」 표시를 달고 있음 | 옛 값을 다시 넣어 되돌린다 |
| 옛 프로모션 %로 계산한 배수가 여러 문서에 남음 | 그 계수로 역산하면 틀린다 |
| 해제한 프로모션이 살아 있는 것처럼 적힘 | Σ가 틀린다 |
| 철회된 공식이 본문에 그대로 있음 | 맨 위 철회 문구를 안 보면 잘못된 지시가 된다 |
| 실행 기록 표에 나중에 바뀐 칸이 남음 | 넣으면 되돌리는 것이다 |
| 「현재」·「지금」만 쓰고 조회일이 없는 스냅샷 | 옛 값으로 굳는다 |

대장에는 문서마다 **현행 / 폐기 / 완료** 상태와 "살릴 것"을 적는다. 문서에 숫자를 넣을 땐 조회일을 같이 넣는다.

## 지켜야 할 선 — 프로필에서 읽는다

- 객실·요일별 목표 입금가와 **어느 경로 기준인지** (최저 경로로 역산하는 것이 기본)
- 하한은 겹으로 적는다: 규칙 하한 · 채널 정합선 · 변동비 · 실적 기준선
- 운영자가 직접 관리하는 세트나 당일 운영 규칙 (미리 걸지 않는다)
- 담당 범위는 **트립닷컴 단독**. 다른 채널은 비교 근거로만 쓴다
- 다른 채널의 요금·공급처를 바꾸는 일은 지시 없이 하지 않는다

목표가 프로필에 없으면 계산 결과만 내고 "목표 미지정"이라고 밝힌다. 목표를 지어내지 않는다.

## 사실만 말하기

- **실측값과 계산값을 반드시 구분해서 쓴다.** 예약 지급액만 실측이다
- **표본이 1이면 「1건에서는 이랬다」라고만 쓴다.** 호텔 사례는 「한 숙소 관측」이라 표시한다
- **역산한 값을 그 역산의 출처와 대조하면 순환논증이다.** 독립된 원본과 대조하고, 없으면 「추정」이라 쓴다
- "저장 안 됐을 것" 같은 추정을 사실처럼 말하지 않는다. 연결이 끊겼으면 서버 값을 다시 읽고 나서 말한다
- 원인을 못 찾으면 「고정값」이 아니라 「원인 미상」이라고 쓴다
- 「데이터가 이상하다」고 결론 내기 전에 내 측정 방법부터 의심한다
- 「A처럼 B를 줘」에서 A는 형식, B는 대상이다. 채널마다 숫자가 다른 작업은 착수 전에 대상 채널을 한 줄로 확인한다
- **매 턴 문서를 남긴다.** 그 턴에서 확인·판정·계산한 것을 프로필의 「기록 위치」에 기록한다
- 예약번호·투숙객 이름·연락처는 결과물과 기록에 남기지 않는다

## 출력 형식

1. **확인한 자료와 시점** — 프로필 / 화면 / 예약 지급액 중 무엇을 봤는지
2. **계수** — r · c · m · 프로모션 OFF 값, 각각의 근거(실측/프로필/미확인)
3. **경로별 표** — 객실 × 요금제 × 경로(유입·국가·회원): Σ · 지급액(계산값) · 목표 대비, 최저 경로 표시
4. **실예약 대조** — 실측 원장 형식
5. **노출 확인** — 일치 N건, 안 뜬 것 M건과 이유
6. **변경 목록** — 무엇을 어떤 순서로(판매가 먼저) 바꾸는지, 변경 전 값, 롤백 순서
7. **확인 필요·미확인 조건**

- 행은 객실 이름으로 확인한다. 왼쪽 고정열과 가운데 영역이 같은 `row-index`를 쓰니 컨테이너를 구분해 읽는다.
- 한 호출에 1~4칸만 넣고, **별도 호출로** DOM값과 React값을 대조한다. 어긋난 칸은 그대로 저장하면 옛 값이 남는다.
- `Runtime.evaluate`는 45초에서 끊긴다. 화면 전환과 재조회를 한 호출에 몰지 않는다.
- 그룹을 바꾼 뒤에는 스크린샷을 찍어 그리드 값까지 확인하고 나서 읽는다. 0개가 읽히면 값이 없는 게 아니라 안 그려진 것이다.
- 입력 전 값과 요금ID를 롤백값으로 적는다.

| 함정 | 대처 |
|---|---|
| 저장 전 새로고침·이동 | 확인창이 떠 탭이 멈출 수 있다. 이탈하지 않는다 |
| 포커스가 저장 버튼으로 흘러간 채 Enter | 저장이 눌린다. Enter를 쓰지 않는다 |
| 저장 뒤 같은 탭에서 옛 값이 보인다 | 저장 실패로 단정하지 말고 **새 탭으로** 읽는다. 재저장에서 오류(`ORA-20106`)가 난 적이 있다 |
| 숨은 모달 문구를 DOM에서 잡아 오판 | 「저장 되었습니다」는 화면으로 확인한다 |
| 이전 모달이 남아 그리드를 가린다 | 보이는 확인 버튼을 닫고 다시 읽는다 |
| 요금 관리 표의 「요금세트」 줄과 「요금」 줄이 한 칸 어긋난다 | 이미 아는 짝으로 맞춰 본다 |

저장 확인은 모달 + 재조회 + 새 요금ID 세 가지로 하고, 최종 확인은 고객 페이지 정가로 한다.
