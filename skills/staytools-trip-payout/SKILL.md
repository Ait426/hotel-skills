# 트립닷컴 — 조사 · 계산 · 콘솔

**이 배포본에는 특정 숙소의 값이 없다.** 숙소 ID·수수료율·프로모션·목표는 전부 그 숙소의 자료에서 온다.
`properties/example-hotel-00000000.json` 은 형식을 보여 주는 **가상 숙소**다. 그 숫자를 다른 숙소 계산에 쓰지 마라.

## 인자 처리 — 이게 최우선이다

숙소 ID(숫자)만 받고 호출되면 **묻지 말고 전체 흐름을 끝까지 돌려라.** 사전 점검 → 측정 → 공식 대조 → property.json → HTML → 전달까지다.

```
/staytools-trip-payout                  로그인된 계정의 숙소를 찾아 조사 → HTML
/staytools-trip-payout 12345678         그 숙소를 조사 → HTML
/staytools-trip-payout 샘플 스테이        이름으로 찾아 조사 → HTML
/staytools-trip-payout 12345678 계산만   조사 없이 저장된 값으로 계산
```

- 숙소가 여럿이고 이름도 없으면 목록을 보여 주고 고르게 한다. 호텔 계약 ID와 고객 페이지 호텔 ID가 다를 수 있으니 둘 다 적는다.
- 로그인이 안 되어 있으면 사용자에게 요청하고 기다린다. 대신 로그인하지 마라.
- 막힌 영역은 `null` 과 `open[]` 에 남기고 나머지를 끝까지 진행한다. 한 영역 실패로 멈추지 마라.
- 목표 입금가처럼 **사용자만 정할 수 있는 값**은 지어내지 않는다. 없으면 비워 두고 보고에 적는다.

### 브라우저 도구가 없을 때 — 자료를 받아서 진행한다

eBooking을 읽을 도구가 없으면 조사를 지어내지 마라. 사용자가 준 자료(화면에서 옮긴 값, 예약 엑셀, 예약 지불 정보)로 `property.json` 을 채워 계산과 HTML 생성까지 한다.

**최소 입력:** 숙소명 · 숙소 ID · 수수료율 c · 회원 할인 m · 요금제별 r · 객실별 판매가 · 프로모션 목록(OFF 칸 값, 적용 국가, 대상 객실).

끝나면 반드시 이 셋을 낸다.
1. HTML 파일 (전달 도구가 없으면 저장 경로)
2. 측정값 표 (각 값이 어느 화면·자료에서 나왔는지 포함)
3. 못 읽은 것과 그 이유

## 먼저 — 무슨 요청인지 가른다

| 사용자가 말한 것 | 할 일 | 읽을 것 |
|---|---|---|
| "입금가 얼마", "요금 얼마로 올려야 하나", "이 프로모션 켜도 되나" | 계산만 | `references/pricing.md` → `scripts/payout.py` |
| "실측했어?", "입금가가 이상하다" | 실측 대조 | `references/measure.md` → `payout.py booking` |
| "우리 요금이 안 보인다", "고객페이지 확인해" | 노출 확인 | `references/portal-map.md` 재판매 구분 |
| "점검해줘", "현황 봐줘", "뭐가 부족해" | 숙소 점검 + 콘솔 | `references/audit.md` → 아래 전체 흐름 |
| "숙소 조사해줘" | 조사 + 콘솔 | `references/portal-map.md` → 아래 전체 흐름 |
| "콘솔 만들어줘", "계산기 만들어줘" | 생성 | `assets/property.example.json` → `scripts/build_console.py` |
| "요금세트", "WINGSCMS" | 운영 입력 | `references/cms.md` |

**계산만 하면 되는 요청에 조사를 돌리지 마라.** 저장된 `property.json` 이나 프로필이 있으면 그 값으로 계산하고, 오래됐을 때만 eBooking을 연다.

## 전체 흐름 (조사부터)

```
1. 사전 점검  로그인 · 숙소 ID · 프로필과 기준 문서 · 요금 모드 확인
2. 측정      My promotions OFF 칸·Details·Logs → 프로그램 → 달력 → 요금제 r → 최근 예약 지불 정보 → 고객 페이지
3. 대조      payout.py booking 으로 공식과 지급액 비교 (허용 오차는 박수만큼)
4. 숙소 점검  audit.md 순서로 노출·요금 경쟁력·정보·리뷰·프로그램 조회 → audit[]
5. 기록      property.json 작성. 경로마다 겹치는 조합을 후보로 적는다
6. 검사      build_console.py --check : 겹침 금지 조합 · 원장 불일치 · 점검 위험·주의 확인
7. 생성      build_console.py → HTML
8. 전달      파일 + 측정값 표 + 점검 결과 + 못 읽은 것
```

## 시작하기 전에 반드시 할 것 세 가지

### 0) 숙소 프로필을 확정하라

작업 폴더나 이 스킬 폴더에 `hotel-profile.md` 가 있으면 읽는다. 없으면 `hotel-profile.example.md` 양식의 항목을
사용자에게 받거나 eBooking 화면에서 읽어 채운다. **프로필에 없는 값은 지어내지 않는다.**
본문과 양식의 숫자는 형식 예시다 — 다른 숙소의 요율·프로모션을 복사하지 마라.

**이 스킬의 공식은 「판매가 입력」 요금 모드 전제다.** 프로필의 요금 모드가 판매가 입력이 아니면 공식을 쓰지 말고
「확인 필요」(`references/pricing.md`)로 보고한다.

### 1) 숙소의 기준 문서를 먼저 읽어라

프로필의 「기준 문서」에 적힌 문서(현행 요금표, 문서 점검 대장)가 있으면 그것부터 읽는다.
운영 문서가 쌓이면 **옛 요금표가 「현행」 표시를 단 채로 남고, 해제한 프로모션이 살아 있는 것처럼 적혀 있다**(아래 「폐기된 문서」).
기준 문서가 없는 숙소면 이번 작업의 결과를 첫 기준 문서로 남긴다.

### 2) 계수를 오늘 값으로 확인하라

**프로모션 %는 고정이 아니다.** 입금가를 말하기 전에 세 곳을 본다.

| 볼 곳 | 위치 | 왜 |
|---|---|---|
| **OFF 칸** | My promotions의 할인 칸 (`nn% OFF`) | 프로모션 **이름의 %는 믿지 않는다.** 한 숙소 관측: 이름과 OFF 칸이 달랐다 |
| **Logs** | Details → Logs | 누가·언제·전후값이 찍힌다. 한 숙소 관측: 트립 담당자 계정이 캠페인·Package를 만들고, 호텔이 바꾼 값을 예고 없이 되돌렸다 |
| **최근 예약** | 예약 상세 지불 정보의 할인 내역 | 할인 ÷ 원래 객실 요금 비율로 OFF 칸을 검산한다 |

프로모션 목록 끝까지 봤다고 끝이 아니다. 조사 순서: My promotions → 프로모션 카탈로그 → 캠페인 탭 → 비즈니스 기회의 프로그램 → 마케팅 계정.

## 공식 요약

```
P'     = 기준 판매가 × r                 ← 고객 페이지 취소선 정가
노출가  = P' × (1 − Σ)                   ← 트립 부담 쿠폰을 빼기 전 손님 가격
지급액  = P' × (1 − c) × (1 − Σ) − A      ← 입금의 정본은 예약 지급액이다
역산   = 목표 ÷ (r × (1 − c) × (1 − 최저경로 Σ))  → 천원 단위 올림
```

- **할인은 덧셈이고, 겹치지 않는 조합끼리는 합계가 큰 쪽 하나만 걸린다.** 비교는 「프로모션 + 회원」 합계로 한다.
- 근거와 예외는 `references/pricing.md` 에 있다. 프로모션을 판단하기 전에 반드시 읽는다.

## 숙소를 어떻게 찾는가 — ID를 묻지 마라

상단에 숙소명이 뜨고, 왼쪽 메뉴 맨 위 숙소명 링크의 고객 페이지 주소(`hotel-detail-숫자`)가 고객 페이지 호텔 ID 다. 계약 ID 는 재무·프로모션 화면에서 읽는다. 둘이 다를 수 있다.
계정에 숙소가 하나면 묻지 말고 그 숙소로 시작한다. 여러 숙소 계정의 전환 화면은 이 스킬을 만들 때 확인하지 못했다. 처음 만나면 `portal-map.md` 에 적는다.
**중간에 질문하지 마라.** 판단이 필요하면 스스로 정하고 무엇을 가정했는지 결과 보고에 적는다. 막힌 영역만 `null` + `open[]` 에 남기고 나머지를 끝까지 한다.
여러 숙소를 한 번에 시켰으면 숙소별로 `properties/{이름}-{ID}.json` 과 HTML 을 각각 만들고 마지막에 비교 표를 낸다.

## 측정할 때 지킬 것

- **화면에서 읽은 것만 적는다.** 모르는 값은 `null` 로 두고 `open[]` 에 "무엇을 어떻게 확인하나"를 적는다.
- **설정 가능 범위와 현재 설정을 섞지 않는다.** "1~40% 설정 가능, 현재 5%"는 두 개의 사실이다. `programs[].range` 와 `setting` 에 나눠 적는다.
- **결론이 뒤집히면 왜 바뀌었는지 남긴다.** `findings[].revised` 에 이전 판정과 정정 사유를 적는다.
- **노출가는 날짜 3개 이상으로 잰다** (`measurements[]`). 우리 요금(직판)만 넣고 재판매 값은 넣지 않는다.
- 투숙객 이름·연락처·예약번호, 담당자 연락처, 비밀번호·쿠키·토큰은 어디에도 적지 않는다.
- 저장·적용·참여·중지·삭제 버튼은 화면을 열어 두는 데까지만 하고 누르는 건 사용자에게 맡긴다(프로필의 버튼 정책이 따로 있으면 그것을 따른다).

## 조사를 마친 뒤

`findings[]` 가 결론이다. 심각도 순으로 정렬하고 각 항목에 **근거**를 붙인다. "사진 태그 2장 누락"은 실측이고 "객실 사진부터 처리"는 판단이다. 둘을 같은 문장에 넣지 않는다.
새로 조사한 숙소는 `properties/{이름}-{ID}.json` (과 프로필 `.md`)으로 남긴다. 다음 계산 요청이 빨라진다. 스킬 폴더에 쓸 수 없으면 사용자의 작업 폴더에 같은 이름으로 저장하고 위치를 알린다.
끝나면 반드시 이 셋을 낸다: ① `SendUserFile` 로 HTML (사용자가 계속 볼 물건이면 Artifact 로도 게시) ② 측정값 표(값마다 화면·자료 출처) ③ 못 읽은 것과 그 이유.

## 계산기

```
python scripts/payout.py forward --rate 200000 --r 0.9 --sigma 40 10 --c 15 --floor 70000
python scripts/payout.py reverse --target 70000 --r 0.9 --sigma 50 --c 15
python scripts/payout.py check   --rate 200000 --r 0.9 --sigma 50 --add 3 5 10 --c 15 --floor 70000
python scripts/payout.py table   --r 0.9 --c 15 --targets 60000 70000
python scripts/payout.py restore --payout 76500 --disc 76500 --c 15 --r 0.9
python scripts/payout.py booking --orig 153000 --disc 76500 --payout 76500 --pprime 180000
python scripts/payout.py routes  --property property.json
```

위 숫자는 형식 예시다. 프로그램 차감은 `--extra` 이고 `--unit` 으로 올림 단위를 바꾼다.

## 콘솔 만들기

`assets/property.example.json` 을 복사해 값을 채운다. `_note` 에 칸마다 쓰는 법이 있다.

```
python scripts/build_console.py property.json --check
python scripts/build_console.py property.json -o 콘솔.html
```

콘솔은 아고다 콘솔과 같은 네 화면(현재 설정 · 계산기 · 요금표 · 실측 기록)을 탭으로 나눈다. 「현재 설정」 맨 위에 요약과 발견 사항(심각도 순)이 오고, 점검 결과, 프로그램(설정 가능 범위 · 현재 설정), 콘텐츠(사진 · 리뷰 · 매핑), 요금제, 노출가 실측이 이어진다. 「계산기」에는 아고다 계산기처럼 중복 규칙을 강제하는 프로모션 조합기와 수수료 조합 비교(`promoGroups` · `commissionParts`)가 붙는다. 조합기는 두 방향(요금 → 입금가, 목표 입금가 → 필요 요금)으로 돌고, 목표 칩(`targets`), 실측 비율 고정 토글(`measurements`), 요일·요금세트별 일괄 표(`rooms[].rates`), 할인·수수료·입금 분해 막대를 갖는다. 아고다 계산기처럼 항목별 할인율 직접 수정, 수수료 슬라이더(`range`)와 켜기/끄기, 올림 단위 전환(100·1,000·5,000원), 금액 단계 분해와 입금계수, 실측 점별 이론값 대조, 요일별 표의 하한 판정(하한 미달 · 턱걸이 · OK)과 필요 요금, 요금 칩(`property.ratePresets` 또는 객실 요금)도 있다. 탭은 주소의 `#p0~#p3` 으로 기억된다. 「요금표」에는 채널별 요금 비교(`channels`)가 붙는다. 그 뒤에 계수, 계산기, 경로별 지급액과 목표 판정, 프로모션, 실측 원장, 미확인 항목이 들어간다. 값이 없는 카드는 자동으로 빠진다.
`--check` 는 아고다 스킬처럼 발견 사항의 근거 누락, 미확인 프로그램의 보고 누락, 예약 0건 요금제, 노출가 실측 비율 어긋남도 잡는다. 또 `verified:false` 가 붙은 모든 칸(묶음 `verified{}` 포함)이 findings·open 에 흔적을 남겼는지, 필수 영역(rooms · measurements · programs · content · ratePlans · findings)이 비었는지, 실측 비율이 범위를 벗어났는지, 최악 조합에서 하한을 지키려면 요금이 얼마여야 하는지 알린다. `--artifact` 를 붙이면 claude.ai Artifact 에 붙일 조각(`-artifact.html`)도 함께 만든다. 겹침 금지 조합, 원장 불일치, 점검 위험·주의는 요청받지 않았어도 보고한다.

## 켜기 · 끄기 판정

프로모션을 판단할 때는 **「무엇과 겹치나」보다 「무엇을 밀어내나」를 먼저** 계산한다.

1. 대상 손님별로 **지금 걸리는 Σ**를 적는다 (경로 × 국가 × 객실 × 회원)
2. 켰을 때 각 손님의 Σ가 바뀌는가. **회원 가산을 더한 값으로 비교**한다
3. **최저경로 Σ가 바뀌는가.** 바뀌면 역산 계수도 바뀐다
4. 객실마다 따로 본다. 모든 객실에 걸면 스위트·조식 요금제에도 똑같이 붙는다. 한 숙소 관측: 스위트 조식 연박 예약의 입금이 같은 방 1박보다 낮아졌다
5. 목표선을 넘는가. 안 넘으면 판매가를 얼마로 올려야 하는지 역산해 같이 제시한다

**프로모션만 켜라고 하고 판매가 이야기를 빼면 사고가 난다.** 끌 때도 같은 표로 본다.

프로그램 대시보드의 예약·매출은 귀속치이지 증분이 아니다. 효과를 단정하지 말고 비용과 귀속 건수만 준다.
숙소의 판단 기준(예: 손님 결제가를 못 내리는 부담은 끈다)이 있으면 프로필에서 읽는다.

## 변경 순서 · 검증 층위

### 계산할 때
1. OFF 칸·Logs·최근 예약으로 현재 값을 확인한다 (못 하면 프로필 값을 쓰고 "미확인"으로 표시)
2. 객실별로 Σ 산정 순서를 밟아 **경로 표**를 만든다
3. **최저경로 Σ로 역산**하고 천원 단위 올림한다. 판매가 하나가 전 경로를 같이 움직이므로 경로별로 따로 맞출 수 없다
4. 올린 판매가로 **다른 경로와 1박 손님의 결제가**가 어떻게 바뀌는지 같이 적고, 재판매에 밀릴 수 있으면 표시한다
5. 환불불가와 무료취소 목표를 동시에 받으면 파생 때문에 둘 다 정확히 못 맞춘다. 앵커 하나를 정하고 다른 쪽 결과를 보고한다

### 요금을 바꿀 때 — 판매가 먼저, 프로모션 나중

프로모션 변경은 고객 페이지에 바로 반영되는 것으로 관측됐다 (시점값, 다를 수 있음).

| 순서 | 사이 구간 | 손실 |
|---|---|---|
| 프로모션 먼저 | 옛 판매가에 새(깊은) 할인 | 🔴 **헐값 판매. 돈이 나간다** |
| **판매가 먼저** | 새 판매가에 옛(얕은) 할인 | 🟡 잠깐 비싸다. **손실 없음** |

되돌릴 때는 반대 순서다. **롤백값은 누르기 전에 적는다.** 값을 바꾼 뒤에는 그 값을 전제로 쓴 옛 문장을 검색해 같이 고친다.

### 검증할 때 — 6층까지 가야 확정이다

```
1층 eBooking 달력(값·판매 토글·재고) → 2층 My promotions OFF 칸·대상·Logs
→ 3층 고객 페이지 정가(객실 × 요금제 × 인원, 1박·2박, 금·토 포함)
→ 4층 안 뜬 것 M건과 그 이유 → 5층 며칠 뒤 Logs·OFF 칸 재확인 → 6층 실예약 지급액
```

**달력부터 본다.** 고객 페이지부터 보면 노출 로직·프로모션·다른 공급처가 섞여 원인을 못 가른다.
보고는 「일치 N건」으로 끝내지 말고 **「안 뜬 것 M건과 이유」**를 같이 낸다. 화면값끼리의 대조는 아직 화면값이다.

## 버튼 정책 — 사용자가 누른다

- **로그인·결제·최종 저장은 사용자가 한다.** 자격 증명은 절대 입력하지 않는다.
- 스킬은 변경 내용과 롤백값을 정리하고 **저장·적용·중지·제출·약관 동의 직전에 멈춘다.**
- 누르기 전 검증을 엄격하게 한다 — 바꾼 행뿐 아니라 안 바꾼 행까지 기대값과 대조한다.
- 사용자가 누른 뒤 화면을 이탈했다 돌아와 서버 값을 다시 읽는다.

프로모션 수정의 「Promotion Agreement」 동의 체크, 리뷰 신고 같은 제출, 트립 문의 발송도 사용자가 한다.

## 🔴 폐기된 문서 — 그대로 실행하면 사고가 난다

운영 문서가 쌓인 숙소에서는 작업 전에 **문서 점검 대장**을 만든다(없으면 이번에 만든다). 이런 문서가 위험하다.

| 유형 | 위험 |
|---|---|
| 옛 요금표가 「현행」·「확정」 표시를 달고 있음 | 옛 값을 다시 넣어 되돌린다 |
| 옛 프로모션 %로 계산한 배수가 여러 문서에 남음 | 그 계수로 역산하면 틀린다 |
| 해제한 프로모션이 살아 있는 것처럼 적힘 | Σ가 틀린다 |
| 철회된 공식이 본문에 그대로 있음 | 맨 위 철회 문구를 안 보면 잘못된 지시가 된다 |
| 실행 기록 표에 나중에 바뀐 칸이 남음 | 넣으면 되돌리는 것이다 |
| 「현재」·「지금」만 쓰고 조회일이 없는 스냅샷 | 옛 값으로 굳는다 |

대장에는 문서마다 **현행 / 폐기 / 완료** 상태와 "살릴 것"을 적는다. 문서에 숫자를 넣을 땐 조회일을 같이 넣는다.

## 지켜야 할 선 — 프로필에서 읽는다

- 객실·요일별 목표 입금가와 **어느 경로 기준인지** (최저 경로로 역산하는 것이 기본)
- 하한은 겹으로 적는다: 규칙 하한 · 채널 정합선 · 변동비 · 실적 기준선
- 운영자가 직접 관리하는 세트나 당일 운영 규칙 (미리 걸지 않는다)
- 담당 범위는 **트립닷컴 단독**. 다른 채널은 비교 근거로만 쓴다
- 다른 채널의 요금·공급처를 바꾸는 일은 지시 없이 하지 않는다

목표가 프로필에 없으면 계산 결과만 내고 "목표 미지정"이라고 밝힌다. 목표를 지어내지 않는다.

## 사실만 말하기

- **실측값과 계산값을 반드시 구분해서 쓴다.** 예약 지급액만 실측이다
- **표본이 1이면 「1건에서는 이랬다」라고만 쓴다.** 호텔 사례는 「한 숙소 관측」이라 표시한다
- **역산한 값을 그 역산의 출처와 대조하면 순환논증이다.** 독립된 원본과 대조하고, 없으면 「추정」이라 쓴다
- "저장 안 됐을 것" 같은 추정을 사실처럼 말하지 않는다. 연결이 끊겼으면 서버 값을 다시 읽고 나서 말한다
- 원인을 못 찾으면 「고정값」이 아니라 「원인 미상」이라고 쓴다
- 「데이터가 이상하다」고 결론 내기 전에 내 측정 방법부터 의심한다
- 「A처럼 B를 줘」에서 A는 형식, B는 대상이다. 채널마다 숫자가 다른 작업은 착수 전에 대상 채널을 한 줄로 확인한다
- **매 턴 문서를 남긴다.** 그 턴에서 확인·판정·계산한 것을 프로필의 「기록 위치」에 기록한다
- 예약번호·투숙객 이름·연락처는 결과물과 기록에 남기지 않는다

## 출력 형식

1. **확인한 자료와 시점** — 프로필 / 화면 / 예약 지급액 중 무엇을 봤는지
2. **계수** — r · c · m · 프로모션 OFF 값, 각각의 근거(실측/프로필/미확인)
3. **경로별 표** — 객실 × 요금제 × 경로(유입·국가·회원): Σ · 지급액(계산값) · 목표 대비, 최저 경로 표시
4. **실예약 대조** — 실측 원장 형식
5. **노출 확인** — 일치 N건, 안 뜬 것 M건과 이유
6. **변경 목록** — 무엇을 어떤 순서로(판매가 먼저) 바꾸는지, 변경 전 값, 롤백 순서
7. **확인 필요·미확인 조건**
