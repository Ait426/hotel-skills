# 입금가 계산 — 공식과 검증

## 공식

```
고객 결제액 = CMS × (1 − Σ)
입금가      = CMS × (1 − Σ) × (1 − 보수)
아고다 표시가(세전) = 고객 결제액 ÷ 세금배수
```

- `CMS` — 채널 매니저가 아고다로 보내는 기준요금
- `Σ` — 그 예약에 실제로 붙은 할인율의 **합** (곱이 아니다)
- `보수` — 아고다가 떼가는 총 커미션
- `세금배수` — 한국은 보통 1.1

## Σ는 덧셈이다 — 아고다가 직접 확인해준다

할인 시뮬레이터(`/promotions/promotionsimulator/{id}`)에 요금과 할인율을 넣어보면 안다.

```
160,000원 · 10% + 10% + 10% + 10%  →  96,000원 (−40%)
```

곱셈이면 104,976원이 나온다. **덧셈이 맞다.** 아고다 프로모션 생성 폼에도
"20% 프로모션에 본 10% 프로모션 중복 적용 시 총 할인은 30%"라고 쓰여 있다.

숙소가 바뀌어도 이 구조는 같다. 다만 **적용되는 프로모션 조합은 숙소마다 다르니 Σ는 매번 새로 세라.**

## 파생 요금제만 곱셈이다

환불불가 같은 **파생 요금제의 %는 Σ에 더하지 않는다.** 기반가(CMS)에 먼저 곱하고, 그 위에 Σ가 얹힌다.

```
파생 요금제 입금가 = CMS × 파생 배수 × (1 − Σ) × (1 − 보수)
```

Maximum Gain은 지금까지처럼 Σ에 더한다. MG도 곱해진다는 관측 기록이 있어 확인 필요 — 실제 예약 내역으로 숙소마다 확인한다.

## 입금가는 쿠폰 전 금액으로 계산한다

```
입금가 = 쿠폰 전 금액(세금 포함) × (1 − 보수)
쿠폰 전 금액(세금 포함) = CMS × (1 − Σ)
```

소비자 페이지의 `원래 요금`이 쿠폰 전 값이다. **손님 결제액(큰 글씨, 1박당 총 금액)으로 계산하지 마라.** 쿠폰만큼 틀린다.
`원래 요금`이 세전 표기면 세금배수를 곱해서 넣는다. 예약 건은 `기준 판매 요금`을 쓰고, 쿠폰 부담 주체는 예약 내역으로 확인한다.

## 최대 할인 상한은 없다

시뮬레이터에 `45 + 25 + 15 + 15 = 100%`를 넣으면 **0원 / −100%**를 그대로 계산한다.
경고도 클램프도 없다. 아고다가 막아주지 않는다는 뜻이니 **Σ 관리는 전적으로 숙소 책임이다.**

## ★ 시뮬레이터의 함정 — Maximum Gain이 빠져 있다

할인 시뮬레이터는 **프로모션만** 다룬다 (메가세일 / 시즌 / 알뜰 / 타겟팅).
Maximum Gain(Beds Network) 같은 **프로그램은 포함되지 않는다.**

화면에 "최대 할인 40%"라고 나와도 MG가 켜져 있으면 실제로는 **40 + MG%** 다.
이걸 놓치면 입금가를 심각하게 과대평가한다. 반드시 프로그램 허브에서 MG 설정을 따로 확인해라.

## 중복 규칙 — 포털 원문

> 이 프로모션은 알뜰 프로모션, 시즌 프로모션 1개, 그리고 각 타겟팅 프로모션 카테고리
> (예: 플랫폼, 멤버십)별 프로모션 1개와 함께 중복 적용될 수 있습니다.

정리하면:

```
Σ = 프로그램(MG 등) + 시즌 계열 max 1개 + 타겟팅 카테고리당 1개 + 알뜰 무제한 누적
```

**핵심은 "프로모션 개수"가 아니라 "카테고리 개수"를 센다는 것.**
시즌 프로모션을 10개 켜도 예약 하나엔 1개만 붙는다. 겹쳐 켜는 건 공짜다.
반대로 **알뜰은 누적**이라 얼리버드 + 장기투숙을 같이 켜면 그대로 더해진다.

## 최악값 Σ 계산법

**프로모션 목록을 먼저 읽는다.** 오늘 소비자 페이지에 없는 할인까지 포함해야 한다.

| 종류 | 걸리는 기준 | 오늘 화면에 없는 이유 |
|---|---|---|
| 예약 기간 할인 (메가세일 등) | **예약하는 날** | 판매 기간이 아직 안 왔다 |
| 리드타임 할인 | 체크인까지 남은 날 | 조회한 날짜의 구간이 다르다 |
| 박수 할인 | 숙박 수 | 조회 박수가 다르다 |
| 고객군 할인 | 고객군·접속 국가 | 조회한 쪽이 대상이 아니다 |

적용 중인 프로모션 목록을 뽑아 이렇게 센다.

```python
Σ_worst = 프로그램합 \
        + max(시즌계열 할인율) \
        + sum(알뜰 할인율) \
        + sum(카테고리별 max(타겟팅 할인율))
```

이 값이 그 숙소의 **바닥**을 결정한다. 목표 입금가를 지키려면:

```
필요 CMS = 목표입금가 ÷ (1 − 보수) ÷ (1 − Σ_worst)
```

파생 요금제가 기준이면 분모에 파생 배수도 곱한다.

**예약 기간 할인으로 깨지는 하한은 투숙일 요금으로 못 막는다.** 언제 투숙하든 그 기간에 예약하면 걸리기 때문이다.
이때는 요금이 아니라 프로모션 쪽(참여 해제, 그 기간 다른 할인 상쇄)으로 대응하고 선택지를 사용자에게 준다.

## 계수는 재서 쓴다

```
실효계수 = 직판 쿠폰 전 금액(세금 포함) ÷ 같은 날짜·같은 요금제 CMS
```

- **재서 쓴다.** 예전 계수를 그대로 가져오지 않는다. 직판 오퍼로만 잰다 (`portal-map.md` 5장).
- **정본으로 삼으려면 서로 다른 날짜·객실에서 3건 이상** 확인한다. 표본 1건으로 정본을 만들지 않는다.
- **계수가 바뀌면 전 요일·전 세트·전 요금제를 다시 계산한다.** 한 요일만 고치면 나머지가 그대로 틀린다.
- **순환논증 주의.** 판매 요금에서 역산한 CMS로 공식을 검증하면 항상 맞는다. CMS는 ARI에서 독립적으로 읽는다.
  `아고다 기본 요금 = CMS = PMS` 일치도 같은 숫자의 복사라 검증이 아니다.

## 공식이 맞는지 검증하는 법 — 3점 선형 확인

숙소마다 한 번은 해라. 30분이면 된다.

1. 같은 객실·같은 요금제로 **CMS가 서로 다른 날짜 3개**를 고른다 (예: 평일/금/토)
2. 각 날짜의 아고다 보유 기준요금을 ARI 캘린더에서 읽는다
3. 각 날짜의 소비자 노출가(원래 요금, 세전)를 소비자 페이지의 **직판 오퍼**에서 읽는다 (`portal-map.md` 5장)
4. `노출가 × 세금배수 ÷ CMS` 를 계산한다

세 값이 **±1원 안에서 같으면** 선형이고 공식이 맞는 것이다. 그 비율이 `1 − Σ`다.
어긋나면 요금제별 세금 처리가 다르거나 프로모션이 날짜별로 다른 것이다 — `open`에 적어라.

## 기준값 역산 — 메가세일 할인액을 쓴다

직판 오퍼에 `메가 세일: ₩ N 할인!` 이 뜨면 거기서 기준값을 역산할 수 있다.

```
메가세일이 10%라면  기준요금(세전) = N ÷ 0.10
```

이 값이 ARI의 어느 요금제와 일치하는지 보면 **그 오퍼가 어느 요금제인지** 확정된다.
요금제가 여러 개일 때 어떤 걸 보고 있는지 헷갈리지 않게 해주는 가장 확실한 방법이다.

**주의:** 요금제에 따라 기준을 세전으로 잡을 때와 세금포함으로 잡을 때가 갈릴 수 있다.
룸온리는 `CMS ÷ 세금배수`에 할인율을 곱한 값이, 부가 요금제는 `CMS` 그대로에 할인율을 곱한 값이
맞아떨어지는 사례가 실제로 있었다. 두 가지 다 계산해보고 딱 맞는 쪽을 채택해라.

## 보수 역산 — 실제 예약에서

```
보수율 = 1 − (입금액 ÷ 판매가)
```

정산서나 예약 상세의 `기준 판매 요금` + 실제 입금액으로 계산한다.
포털에 표기된 보수율과 다르면 프로그램 수수료(AGX 등)가 얹힌 것이다.

## 요금제와 프로모션 — 어디서 값이 정해지는가

요금제 사이의 비율이 이상할 때(부가 요금제가 룸온리의 70% 같은), 원인 후보가 셋이다.
**소거법으로 하나씩 지워라. 추측하지 마라.**

### ① 아고다 요금제의 파생 설정

`/app/pricing-metadata/rateplan/{id}` → 요금제 클릭 → 기본 사항 → **`기준 요금제`**

다른 요금제를 골라 거기서 파생시킬 수 있다. 선택 상태를 확인해라.
`요금제 선택`(미선택) 이면 파생이 아니다 — 아고다가 계산하는 게 아니라는 뜻이다.

같은 화면에서 볼 것: 요금제 종류(기본/맞춤형(대한민국 전용)/도매), 객실 종류 개수,
혜택(조식·주차 등), 자동 연장 여부.

### ② 프로모션이 그 요금제를 건너뛰는가

**프로모션 종류마다 걸 수 있는 제한이 다르다. 이게 헷갈리는 지점이다.**

| 프로모션 종류 | 요금제 제한 | 객실 종류 제한 |
|---|---|---|
| 알뜰 (얼리버드 등) | **가능** — 목록에 `요금제` 항목이 있다 | 가능 |
| 메가 세일 | **없음** — 편집 화면에 요금제 항목 자체가 없다 | 가능 (모두/선택만/선택 제외) |

확인법: 프로모션 목록에서 행을 펼치면 `제한사항` 블록에 `요금제 / 객실 종류 / 중복 적용`이 뜬다.
`모두 적용`이면 제한이 없는 것이다. 메가세일은 이 블록에 요금제가 아예 안 나온다.

### ③ 채널 매니저가 그 값을 그대로 보내는가

①②가 모두 아니면 남는 건 이것뿐이다. CMS 요금관리 그리드에서 그 상품그룹의 값을 직접 읽어라.
WINGSCMS 계열은 `요금세트적용_요금조정`에 증감(+/-) 규칙을 걸 수 있어서,
"룸온리의 −30%" 같은 산식이 거기 박혀 있을 수 있다.

**비율이 전 객실·전 날짜에서 소수점까지 똑같다면 사람이 넣은 값이 아니라 규칙이다.**
어느 층의 규칙인지를 ①→②→③ 순으로 지워가며 찾아라.

### ④ 운영자가 노출가를 보고 역산해 넣은 값인가 ← 반드시 물어봐라

③까지 왔으면 **운영자에게 직접 물어라.** 시스템 오류처럼 보이는 비율이
사실은 사람이 의도해서 넣은 보정값인 경우가 실제로 있었다.
`요금제별 Σ 비대칭`(같은 프로모션이 요금제마다 다르게 먹는 현상) 때문에
원가대로 넣으면 노출가 차이가 원가의 몇 배로 벌어지고, 운영자가 그걸 손으로 되돌려 놓은 것이다.

**이 경우 "잘못된 설정"이라고 판정하면 틀린다.** 대신 지적할 건 아래다.

## 부가 요금제(조식 등)가 룸온리와 안 맞을 때 — 비율을 계산하지 마라

고정 비율로 Σ를 보정하는 구조는 값이 틀린 게 아니라 **구조가 틀렸다.**
Σ는 프로모션을 켜고 끌 때마다 바뀌는데 비율은 고정이니 반드시 어긋난다.
프로모션 하나 바꿀 때마다 비율을 다시 풀어야 한다 — 유지가 안 된다.

**맞는 비율을 계산해서 넘기지 마라. 그 요금제를 유지할지부터 판정해라.**

판정 순서:

1. ARI에서 요금제별 기준요금을 읽는다
2. **메가세일 할인액으로 요금제별 Σ를 각각 역산한다** (`기준요금 = 할인액 ÷ 0.10`)
   → Σ 차이가 크면 그 요금제는 룸온리와 같은 프로모션 환경에 있지 않은 것이다
3. 소비자 페이지에서 두 직판 오퍼의 실제 노출가를 비교한다
4. 예약 현황에서 요금제 필터로 **그 요금제로 실제 예약이 있었는지** 본다

**4번이 결정적이다.**

| 예약 | 노출가 | 판정 |
|---|---|---|
| 0건 | 룸온리보다 비쌈 | **뺀다.** 안 팔리는 상품에 비율 계산 붙이지 마라 |
| 있음 | 룸온리보다 비쌈 | 노출가를 원가 수준으로 내린다 |
| 있음 | 정상 | 건드리지 마라 |

끄는 법은 `measure.md`의 **요금제를 끄는 법** 참고. 되돌릴 수 있는 `적용 해제`를 써라.

**절대 하지 마라:**
- CMS 비율만 보고 "원가와 무관한 산식이니 잘못된 설정"이라고 쓰는 것 — Σ 비대칭을 먼저 재라
- Σ 비대칭을 확인하고도 "맞는 비율은 0.NN입니다" 하고 숫자만 넘기는 것 —
  다음 프로모션에서 또 틀린다. 요금제를 뺄지를 물어라
