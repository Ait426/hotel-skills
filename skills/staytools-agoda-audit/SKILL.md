# 아고다 — 조사 · 계산 · 콘솔

숙소별 숫자는 이 스킬의 `references/`에 없다. **절차와 함정만** 있다.
실제 숫자는 `properties/` 아래 숙소별 파일에 있고, 없으면 포털에서 새로 읽거나 사용자에게 받는다.

**이 배포본에는 특정 숙소의 값이 들어 있지 않다.** `properties/example-hotel-0000000.*` 는
형식을 보여주는 **가상 숙소**다. 그 숫자를 다른 숙소의 계산에 쓰지 마라.
보수율·하한·목표 입금가·프로모션 할인율은 전부 **그 숙소의 값으로 새로 채운다.**

## 인자 처리 — 이게 최우선이다

이 스킬이 **숙소 ID(6자리 이상 숫자)만 받고 호출되면 아무것도 묻지 말고 전체 흐름을 끝까지 돌려라.**
사전 점검 → 11개 영역 측정 → 검증 → property.json → HTML 생성 → `SendUserFile` 로 전달까지.

```
/staytools-agoda-audit                      숙소를 스스로 찾아서 조사 → HTML  ← ID 몰라도 된다
/staytools-agoda-audit 1234567              그 숙소를 조사 → HTML
/staytools-agoda-audit 예시 호텔             이름으로 찾아서 조사 → HTML
/staytools-agoda-audit 1234567 계산만        조사 건너뛰고 저장된 값으로 계산
/staytools-agoda-audit 1234567 사진          사진 영역만 점검
```

### 브라우저 도구가 없을 때 — 자료를 받아서 진행한다

포털을 직접 읽을 도구(브라우저 조작)가 없는 환경이면 조사를 지어내지 마라.
사용자가 준 자료(화면 캡처에서 옮긴 값, 엑셀·CSV, 정산서, 직접 적어준 숫자)로
`property.json` 을 채우고 계산과 HTML 생성까지 한다. 받지 못한 값은 `null` + `open[]` 이다.
**최소 입력:** 숙소명 · 아고다 숙소 ID · 보수 구성(계약 수수료·프로그램 수수료) · 적용 중 프로모션과 할인율 ·
요일(요금세트)별 CMS 요금 · 입금가 하한과 목표.
세금 배수는 따로 받지 못하면 1.1(한국 부가세)로 두고 `verified:false` 로 표시하고, `open[]` 에 "세금 배수 — 확인 방법"을 적는다.
화면에서 읽지 못한 설정 범위(`programs[].range`)·프로모션 ID·객실 ID는 `null` 로 둔다 — 참조 문서의 일반 구조를 그 숙소의 값처럼 적지 마라.

### 숙소를 어떻게 찾는가 — 인자 없이 부르거나 이름만 줬을 때

**절대 사용자에게 ID를 묻지 마라. 포털에 목록이 있다.** (포털을 읽을 수 있는 환경일 때)

1. `/mldc/ko-kr/app/iam/propertysearch` 를 연다 (`{id}` 안 붙는다).
   `snippets.js` 의 `properties()` 로 긁으면 **이름 · ID · 도시 · 판매 상태 ·
   당월 수익 · 평균 1일당 요금 · 콘텐츠 점수**가 한 표로 나온다.
2. **1개면** 묻지 말고 그 숙소로 바로 시작한다.
3. **여러 개면** 표를 보여주고 어느 숙소인지 고르게 한다.
   단, 사용자가 이름을 이미 줬으면 그걸로 매칭해서 바로 시작한다 (부분 일치·영문/한글 둘 다 시도).
4. 이름이 목록에 없으면 그때만 "이 계정에 없다"고 알리고 찾은 목록을 보여준다.

이 페이지가 안 열리면 대안: 헤더 상단 숙소 칩(`숙소명 ID xxxxxxx ⌄`)을 클릭 →
드롭다운 검색창이 **숙소명 또는 숙소 ID** 를 받는다. 맨 아래 `모든 숙소 보기` 가 위 목록으로 간다.

**여러 숙소를 한 번에** 시켰으면(`전부 다 해줘`) 숙소별로 순회하면서
`properties/{이름}-{ID}.json` 과 HTML을 각각 만들고, 마지막에 비교 표를 낸다.

**중간에 질문하지 마라.** 판단이 필요하면 스스로 정하고 무엇을 가정했는지 결과 보고에 적어라.
막히면 그 영역만 `null` + `open[]` 에 남기고 **나머지를 끝까지 진행해라.** 한 영역 실패로 멈추지 마라.
(단, 입금가 하한·목표처럼 **사용자만 정할 수 있는 값**은 지어내지 않는다. 없으면 `null` 로 두고 보고에 적는다.)

끝나면 반드시 이 셋을 낸다.
1. `SendUserFile` 로 HTML (파일 전달 도구가 없으면 저장한 경로를 알려준다)
2. 측정값 표 (각 값이 어느 화면·어느 자료에서 나왔는지 포함)
3. 못 읽은 것과 그 이유

## 먼저 — 무슨 요청인지 가른다

| 사용자가 말한 것 | 할 일 | 읽을 것 |
|---|---|---|
| "입금가 얼마", "요금 올려야 하나", "이 프로모션 켜도 되나" | 계산만 | `properties/{숙소}.md` → `references/pricing.md` → `scripts/payout.py` |
| "점검해줘", "뭐가 부족해", "현황 봐줘" | 조사 | `references/portal-map.md` → `measure.md` |
| "HTML로 뽑아줘", "계산기 만들어줘", "대시보드" | 조사 + 생성 | 위 + `scripts/build_console.py` |
| "다른 호텔도 해줘" | 전체 흐름 | 아래 전체 흐름 |

**계산만 하면 되는 요청에 조사를 돌리지 마라.** 그 숙소 파일이 `properties/`에 이미 있으면
Σ와 보수를 거기서 읽어 바로 계산하고, 값이 오래됐다 싶을 때만 포털을 연다.

## 시작하기 전에

**숙소 ID.** 포털 URL 끝의 숫자다 (`/app/setting/photos/1234567` → `1234567`).
사용자가 모르면 포털 상단 숙소 선택기에 `ID xxxxxxx`로 떠 있다.

**로그인.** 아고다 파트너 포털이 로그인돼 있어야 한다.
안 되어 있으면 **사용자에게 로그인을 요청하고 기다려라. 대신 로그인하지 마라.**
판별법은 `references/portal-map.md` 0장.

**채널 매니저.** CMS(WINGSCMS 등)가 있으면 채널별 요금 비교까지 된다.
없어도 아고다 단독으로 콘솔은 나온다. 빈 값은 생성기가 알아서 그 섹션을 뺀다.

**숙소가 정한 선.** 입금가 하한·요일별 목표 입금가·건드리면 안 되는 요금(예: 운영자가 직접 관리하는 요일)은
숙소마다 다르다. `properties/{숙소}.md` 의 「사용자가 정한 선」에 적혀 있으면 그대로 따르고,
없으면 계산 결과에 "하한 미지정"이라고 밝힌다.

## 공식 (검증 완료)

```
고객 결제 = CMS × (1 − Σ)
입금가    = CMS × (1 − Σ) × (1 − 보수)
표시가(세전) = 고객 결제 ÷ 세금배수      (한국은 보통 1.1)
```

**Σ는 가산이다. 곱이 아니다.** 아고다 할인 시뮬레이터로 확정 —
160,000에 10+10+10+10을 넣으면 96,000(−40%)이 나온다. 곱이면 104,976이어야 한다.
**파생 요금제만 곱셈이다** — CMS에 파생 배수를 먼저 곱하고 Σ를 얹는다 (`references/pricing.md`).

**입금가는 쿠폰 전 금액으로 계산한다.** 손님 결제액으로 계산하면 쿠폰만큼 틀린다.
**소비자 페이지에는 재판매 오퍼가 섞인다.** 객실명이 아니라 오퍼 ID로 직판만 고른다 (`references/portal-map.md` 5장).

**최대 할인 상한은 없다.** 45+25+15+15=100%를 넣으면 0원을 그대로 계산한다.
Σ 관리는 전적으로 숙소 책임이다.

**시뮬레이터에 Maximum Gain이 안 들어간다.** MG는 프로그램이지 프로모션이 아니다.
예를 들어 MG가 35%로 켜져 있으면 화면의 "최대 할인 40%"는 실제로 75%다. 여기서 틀린다.
MG의 실제 %는 숙소마다 다르니 **실제 예약의 프로모션 내역**에서 읽어라.

자세한 건 `references/pricing.md`.

## 측정할 때 지킬 것

**화면에서 읽은 것만 적는다.** 추정치를 넣으면 그 숫자가 나중에 의사결정 근거가 된다.
모르는 값은 `null`로 두고 `open` 배열에 "무엇을 어떻게 확인해야 하는지"를 적어라.
`property.json`의 모든 수치 필드에 `verified` 플래그가 있는 이유다.

**설정 가능 범위와 현재 설정을 섞지 않는다.**
"AGX는 1~40% 설정 가능, 현재 2%"는 두 개의 사실이다.

**결론이 뒤집히면 왜 바뀌었는지 남긴다.** `findings[].revised`에 이전 판정과 정정 사유를 적어라.

**개인정보를 남기지 않는다.** 투숙객 이름·연락처·예약번호는 `property.json`·HTML·보고서에 적지 않는다.
근거로 예약을 가리켜야 하면 "해외 거주 손님 예약 1건"처럼 쓴다. 비밀번호·쿠키·토큰은 어떤 경우에도 기록하지 않는다.

## 버튼은 사용자가 누른다

저장·적용·중지·삭제·신고 — **화면을 여기까지 열어놓고 멈춘다.**
무엇을 누르면 무슨 일이 일어나는지 설명하고, 누르는 건 사용자에게 맡겨라.
읽기는 마음대로 해도 된다.

없는 곳이 섞여 있어 즉석에서 짜면 대부분 빈 배열이 나온다. 먼저 읽어라.
(포털 화면은 바뀔 수 있다. 스니펫이 빈 값을 주면 0건으로 읽지 말고 `open[]` 에 남겨라.)

## 콘솔 만들기

```bash
python scripts/build_console.py property.json -o 콘솔.html
python scripts/build_console.py property.json -o 콘솔.html --check   # 자체 점검까지
```

(`python` 이 없으면 `python3` 로 실행한다. 외부 패키지는 필요 없다.)

- 입력은 `assets/property.example.json` 형식. 필드 설명은 그 파일의 `_note`에 있다.
- 채워진 예시는 `properties/example-hotel-0000000.json` (가상 숙소). **이걸 먼저 열어보고 형식을 흉내내라. 숫자는 가져오지 마라.**
- 없는 섹션은 자동으로 빠진다. 부분 조사여도 돌아간다.
- 출력은 외부 참조 0개(구글 폰트 제외)인 **HTML 한 장**이다.
- `--check`는 필수 필드 누락, 보수 구성 합계 불일치, 실측 Σ 범위 이탈,
  `verified:false`인데 `findings`/`open` 어디에도 없는 항목을 잡는다.

**계산기 품질은 `property.json` 을 얼마나 채우느냐로 갈린다.** 아래를 채우면 계산기가
체크박스 몇 개짜리 위젯이 아니라 실제로 쓰는 도구가 된다.

| 필드 | 없으면 | 채우면 |
|---|---|---|
| `promotions.groups` | `sigmaBreakdown` 으로 체크박스 몇 개만 만든다 | **아고다 중복 규칙을 UI가 강제한다** — 카테고리당 1개는 라디오, 알뜰은 체크박스, 각 항목에 ID·기간·할인율 |
| `commission.parts` | 숫자 입력칸 하나 | AGP 드롭다운·AGX 슬라이더로 **조합을 바꿔보며 비교** |
| `property.targets` `cmsPresets` | 프리셋 버튼 없음 | 목표 입금가 원클릭 |
| `property.floor` | 하한 경고 없음 | 하한 미달을 빨갛게 잡아준다 |
| `weekly` | 요일별 표 없음 | **요일×요금세트별로 지금 입금가·목표용 CMS·판정**을 한 번에 |
| `measurements` `measurementNotes` | 실측 대조 없음 | 이론 Σ vs 실측 차이 + Σ 실측 고정 토글 |

### property.json 쓸 때 틀리기 쉬운 것 — 실제로 다 겪었다

**null 을 넣으면 안 되는 자리가 셋 있다.** `property.targets[].v` · `property.cmsPresets[]` ·
`commission.parts[].pct`. 값이 없으면 **그 항목을 통째로 빼라.** (생성기가 걸러내긴 하지만
"모르면 null" 원칙이 여기선 틀린 답이다.) `content.mapping.total` 처럼 화면에 안 나오는
총계도 키를 빼면 `—` 로 나온다.

**계산기는 `commission.total` 이 아니라 `parts` 합으로 돈다.**
`total` = 정산으로 확인된 보수, `settingTotal` = 포털 설정값. 둘이 다르면 둘 다 적어라.
계산기는 `parts` 합(= 포털 설정)으로 열린다 — **하한을 지키려면 높은 쪽이 안전하다.**
개별 항목을 끄면 확인된 값으로 볼 수 있다.

**보수에 기본값은 없다.** `parts` 도 `total` 도 비어 있으면 계산기의 보수가 0%로 열린다.
이 상태의 입금가는 과대평가다 — 정산에서 보수를 확인해 채우기 전에는 결과를 입금가라고 부르지 마라.

**광고 숙소·부킹홀딩스 광고는 `parts` 에 넣지 마라.** 광고비는 입금가 공식 밖이다
(`programs.md` 1장 세 갈래). 넣으면 입금가가 통째로 틀린다.

**`single` 그룹에 실제로 2개가 켜져 있을 때** (International Rate + US 처럼):
예약 1건엔 어차피 1개만 붙으니 `on:true` 는 하나에만 주고, 나머지는 `tag` 에 "적용 중"을 적어라.

**`activeCount`(포털 표시 건수)와 `active[]`(식별한 것)가 다르면** 그대로 두고 `open[]` 에 남겨라.
숫자를 맞추려고 지어내지 마라.

**콘솔과 `payout.py` 의 올림 단위가 다르다.** 콘솔은 `property.roundUnit`(기본 5,000원) 단위로, `payout.py` 는 100원 단위로
필요 CMS를 올림한다. 보고서에 두 값을 같이 쓸 때는 어느 쪽인지 밝혀라.

**`ratePlans` 와 `rooms[].plans` 는 다른 것이다.** 전자는 요금제 인벤토리(ID·상태),
후자는 요금제별 가격. 요금제 6개 중 ARI 가격이 하나뿐이어도 인벤토리는 `ratePlans` 에 다 남는다.

**`programs[].verified:false`** 를 주면 프로그램 표에 `미확인` 배지가 붙는다.
`--check` 는 그 항목이 `findings`/`open` 어디에도 없으면 따로 경고한다.

`groups[].mode` 는 셋이다 — `locked`(항상 적용·MG), `single`(카테고리당 1개·라디오),
`multi`(누적·체크박스). **아고다 중복 규칙을 여기에 인코딩해라.** 그래야 켤 수 없는 조합을
계산기가 애초에 못 만든다.

## 계산기 단독 사용

보수·하한·목표는 **그 숙소의 값**을 넣는다. 아래 숫자는 형식 예시다.

```bash
python scripts/payout.py forward --cms 150000 --promos 55 --commission 20 --floor 50000   # CMS → 입금가
python scripts/payout.py reverse --target 60000 --promos 55 --commission 20                # 목표 → CMS
python scripts/payout.py check   --cms 150000 --promos 55 --commission 20 --floor 50000    # 프로모션 추가 영향
python scripts/payout.py table   --commission 20 --targets 50000 60000 70000               # Σ별 안전선
python scripts/payout.py commission --sale 100000 --payout 80000                           # 예약에서 보수 역산
```

## 조사를 마친 뒤

`findings` 배열이 결론이다. 심각도 순으로 정렬하고 각 항목에 **증거**를 붙여라.
"사진 태그 27건 누락"은 실측이고 "디럭스부터 처리하라"는 판단이다. 둘을 같은 문장에 넣지 마라.

새로 조사한 숙소는 `properties/{이름}-{ID}.md` 와 `.json` 으로 남겨라. 다음 계산 요청이 빨라진다.
(스킬 폴더에 쓸 수 없는 환경이면 사용자의 작업 폴더에 같은 이름으로 저장하고 위치를 알려준다.)

`SendUserFile`로 HTML을 보내고, 사용자가 계속 볼 물건이면 Artifact로도 게시해서 주소를 준다.
