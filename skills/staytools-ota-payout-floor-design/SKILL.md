# OTA 입금가 하한 설계

「최대 할인을 받아도 입금가 X원은 유지해야 한다」 같은 지시를 받았을 때 쓴다.
채널 무관(부킹·익스피디아·아고다·트립) — 곱셈 구조인 OTA라면 같다.

## 0. 입력 — 숙소의 값으로 받는다

이 스킬에는 특정 숙소의 숫자가 없다. 계산 전에 아래를 받는다. 본문의 숫자는 가상 숙소의 예시다.

| 입력 | 설명 |
|---|---|
| 판매가 | 채널에 보내는 기준 요금 (요금세트·객실별) |
| 입금 계수 | 노출가(또는 결제액) → 입금가 환산 계수. 실예약 정산으로 확인한 값인지 추정인지 표시 |
| 요금제 배수 | 환불불가·주간 등 요금제가 먹는 폭 |
| 할인 구조 | 어떤 할인이 있고, 가산(Σ)인지 곱셈인지, 같은 카테고리는 하나만인지 |
| 목표 | 입금가 하한, (있으면) 헤드라인 목표 |
| 부가세 기준 | 입금가가 부가세 포함인지 제외인지 |

**빠진 값은 임의로 채우지 않는다.** 없으면 묻고, 답을 못 받으면 "미확인"으로 두고 그 값에 의존하는 결론은 확정이라고 쓰지 않는다.

## 1. 먼저 최고가 칸부터 검증한다 (가장 흔한 실수)

하한 지시를 받으면 반사적으로 **최심 칸(최대할인 칸)**만 계산하게 된다. 틀렸다.

OTA에는 사다리 순서 제약이 있다 — `평시할인 ≤ 사전할인`, `공개 ≤ 회원`.
그래서 항상 **최고가 ≥ 최심 노출가 ÷ 요금제배수**다.

→ **하한을 올리면 최고가가 반드시 같이 끌려 올라간다.**
→ 최고가 칸의 입금가부터 계산해서, 이미 하한 아래면
   **「이건 하한 조정이 아니라 요금 인상입니다」**라고 먼저 말한다.

예: 하한 입금 90,000원을 요구받았는데 그 채널의 **최고가 칸조차 입금 86,100원**이었다
(판매가 200,000 × 타겟 0.75 × 평시 0.70 × 입금 계수 0.82).
최대할인 칸만 보면 안 보이는 문제다.

## 2. 총 할인 예산으로 환산한다

곱셈이 여러 단이라 할인율을 하나씩 보면 감이 안 온다. 한 줄로 바꾼다.

```
필요 노출가 하한 = 입금 하한 ÷ 입금 계수
필요 노출가 하한 ÷ 판매가 = 남길 계수
1 − 남길 계수              = 총 할인 예산(%)
```

예: 판매가 200,000 · 입금 하한 80,000 · 입금 계수 0.82 → 노출 97,561 → 계수 0.488 → **예산 51.2%**.
현재 최심 칸이 58.0%를 쓰고 있었다면 → **「6.8%p 초과」** 한 문장으로 정리된다.

**현재 사용분은 최심 칸의 노출가로 잰다**: `1 − 최심 노출가 ÷ 판매가`. 요금제 배수가 먹는 폭도 여기에 들어간다
(배수를 빼고 할인율만 세면 초과가 안 보인다).

논쟁이 「어느 할인을 몇 %p 깎을까」라는 배분 문제로 바뀐다.
예산이 음수면 할인 조정으로는 불가능하다 — **판매가 인상**이 필요하다고 말한다.

## 3. 표를 채우기 전에 부등식을 쓴다

**이게 이 스킬의 핵심이다.** 시나리오 표부터 만들면 자기도 모르게 전제를 굳혀버린다.

```
최심 노출가 / 헤드라인 노출가  ≥  목표하한 / 목표헤드라인

좌변 = 요금제배수 × (1 − 최심할인율) / (1 − 헤드라인할인율)
```

- **헤드라인** = 손님이 평소 가장 먼저 보는 칸(보통 기준 요금제 × 평시 공개 할인). 헤드라인 목표를 받지 못했으면
  "현재 헤드라인 칸을 유지한다"고 가정하고, 가정이라고 적는다.
- **요금제 배수**(환불불가·위클리 등)가 이미 상당 폭을 먹는다. 0.95면 5.3%(= 1 ÷ 0.95 − 1).
- 남는 폭 = `(목표헤드라인/목표하한) × 요금제배수 − 1`
- 예: 하한 60,000 · 헤드라인 66,000 · 배수 0.95 → **사다리에 남는 폭 4.5%뿐** → 단계를 여러 개 둘 여유가 거의 없다.

부등식을 써 놓으면 **자유 변수가 무엇인지 바로 보인다.**

## 4. 「불가능」이 나오면 내가 깐 전제를 의심한다

실패 사례 — 목표 입금가를 요구받고 「하한과 충돌해서 불가능」이라고 답했다. **틀렸다.**
원인은 계산에 **「회원 할인 = 공개 할인 + 고정 폭」**이라는 전제를 무의식적으로 넣은 것.
그건 직전 설계의 우연한 값이었을 뿐 채널의 제약이 아니었다.

전제를 걷어내니 **할인 하나만 올려서 그대로 달성**됐다.

체크리스트:
- 이 제약은 **채널이 강제한 것**인가, 내가 이전 설계에서 가져온 것인가?
- 채널이 강제하는 것만 남긴다 (예: 국가별 할인율의 허용 범위, 모바일 최소 할인율, 정수만 입력).
- **틀린 판정은 문서에 정정을 남긴다.** 안 그러면 다음 세션이 오답을 물려받는다.

## 5. 채널 제약을 먼저 확인한다

| 제약 | 확인할 것 |
|---|---|
| 할인율 범위 | 채널이 허용하는 상·하한. 이미 상한이면 그 레버는 못 쓴다 |
| 정수 여부 | 대부분 정수만. 21.75%는 못 넣는다 |
| 중복 규칙 | 가산(Σ)인가 곱셈인가. 같은 카테고리는 하나만인가 |
| 요금제 배수 | 프로모션 화면이 아니라 별도 화면에 있는 경우가 많다 |
| 부가세 기준 | 입금가가 부가세 포함인지 제외인지. 채널마다 다르다 |

화면·공식 안내·실예약 중 어디서 확인했는지 적는다. 확인하지 못한 제약은 "미확인"이다.

## 6. 결과를 보고할 때

항상 이 셋을 같이 낸다.

1. **바뀔 값 목록** — 화면에서 무엇을 몇 %로 고칠지
2. **결과 표** — 칸별 노출가 / 입금가 / 하한 대비 여유
3. **대가** — 무엇을 잃는지. 사다리가 압축되면 사전예약·회원 유인이 얼마나 줄어드는지 숫자로

그리고 **되돌리기 절차**를 한 줄로 남긴다.

## 7. 검증

설정 화면이 아니라 **소비자 페이지에서 역산**해 확인한다.
계산값과 실측값이 **원 단위로 일치**할 때까지 맞춘다. 몇 백 원 차이가 나면 빠뜨린 계수가 있다는 뜻이다.

흔히 빠뜨리는 계수: 요금제 배수 · 숙박인원 계수 · 부가세 · 접속 위치별 요금.

화면을 볼 도구가 없는 환경이면 계산값만 내고 **"실측 미확인 — 소비자 페이지에서 이 날짜·인원으로 확인 필요"**라고
조회 조건까지 적어 준다. 계산값을 실측이라고 쓰지 않는다.
